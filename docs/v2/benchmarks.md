# Benchmarks

Four implementations of the same five models, and a rule: **nothing is timed until every
engine agrees on every number.**

This page is the methodology and the caveats. The numbers themselves are regenerated by
`python -m bench` in `benchmarks/` and live in
[`benchmarks/results/results.md`](https://github.com/RatulMaharaj/predictable/blob/main/benchmarks/results/results.md)
and `results.json`; the headline extracts are reproduced below with the machine they were
taken on named, because a benchmark number without a machine attached is decoration.

Normative source: `03-engine.md` §11.

---

## 1. The gate comes first

A performance claim is only interesting if the fast engine is computing the right thing.
So the benchmark is built the other way round from most: it is a **correctness harness that
also records timings**, and the timings are a side effect of a comparison that has already
passed.

Concretely, `python -m bench`:

1. runs all four engines on every scenario at `M ∈ {1, 25}` — and predictable at
   `M = 1000` as well, to cross its 1024-row chunk boundary — collecting **every output for
   every modelpoint for every period**, the whole result set rather than a summary.
   cashflower and modelx stop at the 25-policy lattice because they project one policy at a
   time with no state shared between policies, so their answer for a policy cannot depend
   on how many others are in the file;
2. compares each engine against the NumPy reference to `1e-9`;
3. and only then times the scenarios that passed. A scenario whose engines disagree is
   **not timed at all**, and the report says so in place of its numbers.

The reference is NumPy, not predictable. That is deliberate: the gate has to be able to
fail predictable, and it cannot do that if predictable is the yardstick. The NumPy
reference is in turn pinned to the committed goldens under `models/*/expected/` — it
reproduces them exactly, to the last bit — so the chain terminates in something that was
checked in and reviewed rather than in an opinion formed at run time.

### The metric, and why it is not cell-relative

For each component, the error is

```text
err = max |a − b|  /  max( max |b| , floor )
```

— the largest absolute difference anywhere in the component, over the component's **own
scale**.

A per-cell relative error sounds stricter and is in fact useless here. `reserve` after a
policy has run off is a number like `1e-17`: two engines that differ in the last bit of it
differ by 100% *relatively*, while differing by `1e-17` in a component whose scale is
thousands. A cell-relative gate would either fail on that or need an arbitrary
"ignore small cells" escape, which is the same judgement call made less visibly. The
scale-relative form asks the question a reviewer actually asks — *is this component wrong
by an amount that matters against the size of the component?* — and needs no escape hatch.

`floor` is `1e-12` normally. For a component that is **solved to zero by construction** it
is `1.0`, which makes the comparison absolute: `term_solve`'s `bel` is driven to zero by
the solver, has no scale of its own, and the honest test is against the solve's own
tolerance (`1e-8` in `models/term_solve/run.pir`). Those components are named explicitly in
`bench/gate.py`; there is no automatic detection and no silent widening.

`benchmarks/tests/test_gate.py` proves each of these behaviours, including that a `1e-8`
relative difference fails.

## 2. The contenders

| engine | what is measured | version |
|---|---|---|
| **predictable** | `predictable run run.pir` as a subprocess — parse, check, plan, table build, modelpoint load, projection, Parquet write | the workspace build |
| **cashflower** | the model assembled and run through cashflower's own pipeline, in process | 0.10.8 |
| **modelx / lifelib** | a modelx model built from the same formulas, in process | modelx 0.32.0, lifelib 0.14.0 |
| **NumPy reference** | a hand-written vectorised implementation, in process | NumPy 2.0.1 |

Prophet is not benchmarked: there is no licence to publish numbers, and the Prophet story
in predictable is the *migration* demo, which is about correctness and time-to-model rather
than throughput.

### The models are the reference models

Every predictable run in this benchmark uses the **committed** `.pir` build, assumption set
and tables from `models/<scenario>/`. Only `data/modelpoints.csv` is regenerated at size
`M`, from the same lattice generator (`models/tools/make_fixtures.py`) that produced the
corpus. The consequence worth stating: the `model_digest` of a benchmark run is byte-
identical to the one in `models/<scenario>/expected/summary.json`. There is no
benchmark-special model.

The other three engines are hand-written transcriptions of those same models, in each
framework's idiom, kept in the repository side by side so a reader can check the
transcription rather than take it on trust:

- `benchmarks/bench/engines/numpy_ref.py`
- `benchmarks/bench/engines/cf_models/*.py`
- `benchmarks/bench/engines/mx_models.py`

They share their tables and their assumption sets with predictable through
`bench/basis.py`, so a disagreement between two engines is always a disagreement about the
*model*, never about the inputs.

## 3. The scenarios

| # | scenario | basis | periods | components | what it exercises |
|---|---|---|---:|---:|---|
| 1 | `term_annual` | annual | 40 | 22 | lookups, recursion, `npv`, the `init` back-channel |
| 2 | `term_monthly` | monthly | 480 | 25 | the `t`-loop constant |
| 3 | `savings_monthly` | monthly | 360 | 49 | an account value, `Select`-heavy branching, four lookups a month |
| 4 | `ifrs17_gmm` | monthly | 360 | 75 | the IFRS 17 GMM: CSM, RA, coverage units, **two substage levels** |
| 5 | `term_solve` | annual | 40 | 22 | `[[solve]]` — the outer loop, and its cost |

Full actuarial documentation for all five is on
[the reference models page](reference-models.md).

### Sizes

`M ∈ {1, 100, 1000, 10 000, 100 000, 1 000 000}`.

`M = 1` is not padding. It is the size a developer iterating on a model actually feels, and
it is the only column where per-run overhead — parse, check, plan, table build, process
start — is visible rather than amortised away.

`M = 10 000 000` is **not run here**, and the tables say so rather than quietly stopping at
`1e6`. It is the CI-runner size of `03-engine.md` §11.3. Until it has been run there, this
repository publishes no number for it.

Neither is `M = 1 000 000` on the three 360- and 480-period scenarios, and the reason is
measured rather than assumed. `emit = "outputs"` means predictable writes **every declared
output for every modelpoint for every period**, so on this workstation:

- `savings_monthly` at `M = 100 000` writes a 2 GB `results.parquet`;
- `ifrs17_gmm` — 45 declared outputs over 361 periods — writes 2.6 GB at `M = 100 000`,
  more than the free disk, so it is capped at `M = 10 000`;
- `ifrs17_gmm` at `M = 1 000 000` is killed for memory before it finishes.

Those are facts about this machine and about the emit setting, not about the kernel, and
they are stated here rather than hidden behind an absent row.

Each engine additionally has a per-scenario size cap, recorded in `bench/scenarios.py` and
reported in the "Not run" section of the results. A scalar Python engine projecting a
360-period model over a million policies is a multi-day run; capping it is honest, and the
cap appears next to the numbers rather than as a silently missing row.

## 4. What is measured

- **Wall time**, cold and warm. The first measured run is reported separately as the cold
  one; the published figure is the **median** of the warm runs, with the min–max spread
  beside it. Not the mean — one scheduler hiccup moves a mean and does not move a median,
  and a benchmark that reports only a mean is reporting the hiccup.
- **modelpoint-periods per second**, `M × (T + 1) / median`. The size-independent number,
  and the one worth quoting.
- **Peak RSS**, sampled at 10 ms over the whole process tree — harness plus children. It
  therefore carries a common ~100 MB interpreter floor for every engine, and should be read
  as an upper bound with a constant offset rather than as an engine's own footprint.
- **Thread scaling** for predictable, `threads ∈ {1, 2, 4, 8}`, taken at the largest size
  each scenario reaches. Thread scaling at `M = 1` would measure thread startup.

At sizes above `M = 1000` the number of warm repeats is reduced, because a single run takes
minutes; every such row carries a note saying how many runs its median is over. A median of
one is a measurement, not a median, and it is labelled as one.

## 5. Caveats — read these before quoting a number

These are the ways in which the comparison is *not* like-for-like. They are listed first,
not in a footnote, because every one of them is a way the headline number could mislead.

**predictable pays for its output; the others do not.**
predictable is timed through the CLI, so its number includes parsing, checking, planning,
building the tables, loading the modelpoints and writing `results.parquet` — and
`emit = "outputs"` means it writes *every declared output for every modelpoint for every
period*. At `M = 100 000` on `savings_monthly` that is a 2 GB result file, and the write
dominates the run. cashflower is timed in process with aggregation on, and modelx and the
NumPy reference are timed computing values and discarding them. **The engines are not doing
the same amount of I/O**, and the difference favours the other three.

**cashflower's file I/O is excluded.** The models are driven through cashflower's own
pipeline (`get_variables` → `determine_calculation_order` → `Model.run`) rather than
through `cashflower.run()`, which requires a project layout on disk and writes CSV. This
skips cashflower's own reading and writing — again in cashflower's favour.

**`term_solve` compares roots, not solvers.** predictable solves with Brent; the other
three use bisection on the same bracket with the same iteration cap. They converge on the
same premium — which is what the gate checks — but Brent gets there in far fewer model
evaluations, so `term_solve` timings measure *the solver as much as the engine* and should
not be read as a throughput comparison.

**`ifrs17_gmm` has only two implementations.** predictable and the NumPy reference. It is
the scenario whose structure — a whole-projection reduction feeding a forward recursion
that is then reduced again — is exactly what a single-pass scalar framework is worst at
expressing, and transcribing it faithfully into cashflower and modelx is a project of its
own rather than a benchmark entry. The gate still runs for it, against NumPy; the
cross-engine columns are simply absent, and the results table says so.

**modelx is memory-bound, not compute-bound, at scale.** modelx retains every computed cell
for dependency tracing, so the harness projects in batches of 250 policies and discards the
model between batches. That is a property of modelx's design rather than a tuning choice,
but it does mean the modelx figure includes model construction amortised over 250 policies.

**One machine, one run.** The numbers below were taken on a single workstation, not on a
fixed CI runner. Absolute figures will move on other hardware; the ratios are the durable
part, and even those should be re-measured before being quoted.

**The scale-relative gate metric is a judgement.** It is defended in §1 and tested, but it
is a choice, and a reviewer who wants cell-relative comparison can change one constant in
`bench/gate.py` and see what happens.

## 7. Reproducing

```console
$ cargo build --release -p predictable-cli
$ cd benchmarks
$ uv venv .venv --python 3.12
$ uv pip install --python .venv/bin/python cashflower lifelib modelx numpy pandas pyarrow pytest
$ .venv/bin/python -m bench --gate-only        # the part that must never be skipped
$ .venv/bin/python -m bench --repeats 5 --threads 1,2,4,8
$ .venv/bin/python -m pytest tests -q          # the benchmark's own regression suite
```

`python -m bench` exits non-zero if the gate failed, which is what makes it usable as a CI
step: a divergence between predictable and an independent implementation of the same model
breaks the build, and the write-up of the divergence is the deliverable.

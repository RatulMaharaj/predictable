# The conformance corpus

`predictable` v2 has one executable artefact — the IR, a `.pir` file — and one specification for it,
`docs/design/01-ir.md`. The **conformance corpus** in `conformance/` is the bridge: a set of
hand-written `.pir` modules, each paired with the canonical form it must format to and the exact
diagnostics it must produce.

It was written **from the spec, before the parser and the checker existed**. That ordering is the
whole point. If the corpus were generated by running the tools, it would record what the tools do,
and "the tools do what they do" is not a test. Written first, it records what the tools *must* do, so
the first time the checker disagrees the corpus is the arbiter.

!!! note "For contributors"
    This page is the contributor guide. The normative contract — the exact file formats — lives in
    `conformance/README.md` and wins where the two differ.

## What is in it

29 cases: 8 valid models and 21 invalid ones, one error class each.

| Group | Cases | Covers |
|---|---|---|
| Valid | `v01`–`v08` | the smallest well-formed model; the term-assurance worked example; a monthly model; every `Expr` node and every builtin; the `fmt` rules; every table policy and resolver; every lint; the full run configuration |
| Invalid | `e01`–`e21` | cycles, shapes, units, timing, table misses, forward references, presence bits, sandbox escapes, product-manifest and run-config errors |

The four cases most worth reading first:

- **`valid/v01-minimal-scalar`** — the smallest thing that runs: a timeline, one modelpoint field,
  one assumption, one `Scalar` output, plus the `[product]` and `[run]` files.
- **`valid/v02-term-assurance`** — the model from `01-ir.md` §6, complete with a real mortality
  table, discounting, and a reserve recursion that reads `reserve[t-1]` and is seeded through `init`
  from a stage-2 `npv`. If you want to learn what a `.pir` file looks like, read this one.
- **`valid/v04-expressions`** — every builtin in the closed 1.0 function set, used exactly once. It
  is the checklist for anyone implementing the evaluator.
- **`invalid/e01-cycle-same-period`** — the two-line model that must produce the `E0201` message.

## Anatomy of a case

```
conformance/valid/v02-term-assurance/
  case.toml            metadata: kind, title, spec citations, entry files
  schema.pir           timeline, enums, modelpoint fields, assumptions, tables
  model.pir            the components
  base.pir             the assumption set
  product.pir          the [product] block
  run.pir              the [run] block
  tables/*.csv         the real table content, hashed into the declaration's digest
  data/*.csv           modelpoints
  expected.diag        the diagnostics that must be produced — here, none
```

Two expectation files carry the contract.

### `expected.diag`

One diagnostic per line:

```
warning W0103 model.pir:72:9 adding a `start` flow to an `end` flow
```

That is: severity, code, the file and 1-based line/column of the **primary span**, and a substring
the rendered message must contain. Comparison is **exact set equality** — an unexpected extra
diagnostic fails the case, which is what keeps a checker from becoming noisy. Columns follow the
spec's own rendering: for a quoted TOML value the span starts at the first character *inside* the
quotes, so in `expr = "bel * 1.05"` the span on `bel` is column 9.

Where `01-ir.md` fixed the behaviour but not the number, the corpus originally used a **family
wildcard** — `E05xx` for any code in the pass-5 (types, units, timing) family — with the rule that
when the diagnostics registry assigned the real number, the wildcard would be replaced by the exact
code in the same commit. That happened when the checker landed, so every line now names an exact
code:

```
error E0502 model.pir:41:9 rates on different bases cannot be added
```

The classes that were numbered then are `E0030` (illegal index form), `E0203`–`E0205` (resolution,
shadowing, horizon), `E0501`–`E0503` (unit arithmetic), `E0504`–`E0505` (lookup keys) and
`E0506`–`E0509` (timing tags, zeroless lag). Codes that `01-ir.md` fixes itself — `E0101`,
`E0105`–`E0108`, `E0201`, `E0202`, `E0301`, `E0305`, `E0402`–`E0404`, `E0602`, `E0801`, `E0902`,
`E0903`, `E1402`, `W0101`–`W0105` — were always written out in full.

### `*.pir.expected`

`fmt(model.pir)` must equal `model.pir.expected` byte for byte. **If the file is absent, the input
is its own canonical form** — every input in the corpus is authored canonically except
`valid/v05-canonical-fmt`, which exists to exercise the formatter:

```toml
# input
[[component]]
expr = "escalated[t-1]*(1.050 + 0.000)"
name = "escalated"
...

# model.pir.expected
[[component]]
name = "escalated"
...
expr = "escalated[t-1] * (1.05 + 0.0)"
```

Key order inside a `[[component]]` is fixed (`name, kind, dtype, shape, unit, timing, init, expr,
doc, tags, output`); binary operators get single spaces; redundant parentheses go, except the ones
disambiguating mixed `*`/`+`, which are preserved as written; floats round-trip shortest.

## How the corpus is used

| If you are building… | The corpus asserts |
|---|---|
| the parser | every valid input parses; every parse-error case reports the expected code and span |
| `predictable fmt` | `fmt(input)` equals the expected canonical form, and `fmt(fmt(x)) == fmt(x)` |
| the checker | the diagnostic set equals `expected.diag`, code for code and span for span |
| the engine | the `runtime = true` cases execute and produce byte-identical results on every determinism target |

A failing case has exactly two honest resolutions: fix the tool, or change the corpus **and cite the
spec section that justifies it in the commit message**. Editing an `.expected` file to match what the
code happens to do is how a specification quietly becomes a changelog, and review should treat it as
such.

## Adding a case

1. Take the next free number in `valid/` or `invalid/`. Numbers are identities: never reused, never
   renumbered when a case is inserted.
2. Write the `.pir` in **canonical form**, unless the case is about `fmt` or about a parse error
   (set `fmt = false` for the latter — an unparseable file has no canonical form).
3. Cite the spec section in `case.toml`'s `spec` list. A case with no citation is not a conformance
   case; it belongs in the implementation's own unit tests.
4. Register it in `conformance/index.toml` with its expected codes.
5. Run the corpus self-check:

    ```console
    $ python3 conformance/check_corpus.py
    29 cases checked, 0 problems
    ```

    It parses no `.pir` file — it verifies that every case is registered, that every span in an
    `expected.diag` points at a line and column that exist and start a value rather than landing on a
    quote or an `=`, that every code is either normative or a legal family wildcard, that diagnostics
    are sorted, that valid cases expect no errors and invalid ones expect at least one, and that
    every `.pir` obeys the canonical text rules (UTF-8, LF, one trailing newline, no trailing
    whitespace). It is the only thing here that can fail before the tools exist, so run it on every
    edit.
6. Keep it minimal — one error class per invalid case. Someone will read your case at 2am while
   debugging a checker regression, and a 200-line reproduction is not a reproduction.

## Worked example: adding an error case

Suppose the spec says `count_while` takes a `bool` predicate and you want that pinned.

```toml
# conformance/invalid/e22-count-while-dtype/case.toml
name  = "e22-count-while-dtype"
kind  = "invalid"
title = "count_while over a non-bool predicate"
spec  = ["01-ir.md §2.8"]
entry = ["model.pir"]
fmt   = true
```

```toml
# conformance/invalid/e22-count-while-dtype/model.pir
[[component]]
name = "years_in_term"
kind = "Output"
dtype = "i64"
shape = "PerMP"
unit = "count"
expr = "count_while(premium_income)"
```

```
# conformance/invalid/e22-count-while-dtype/expected.diag
error E05xx model.pir:31:9 `count_while` takes a `bool` predicate
```

Count the line number in the file you just wrote, put the column at the first character inside the
`expr` quotes, and register the case in `index.toml`. That is the whole workflow.

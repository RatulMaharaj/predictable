# The reference models

`models/` holds five worked models. They are the corpus everything else in predictable is
tested against — the benchmarks, the model diff, the run diff, the explorer screens and the
launch demos all point at these five directories — so they are documented here the way a
model would be documented for a reviewing actuary: product, basis, formulas, and the
identities each one is supposed to satisfy.

Normative sources: `03-engine.md` §11.2 (the five scenarios), `01-ir.md` §6 (the worked
example the first of them is drawn from).

!!! warning "Synthetic, and not a basis"
    Every table and every modelpoint file under `models/` is generated by
    `models/tools/make_fixtures.py` from a closed-form law. The mortality basis is a
    Makeham curve with invented sex and smoker loadings. It is smooth, monotone and
    reproducible, which is what a test corpus needs, and it is **not** a published table
    and must not be used to price anything.

---

## 1. What is in each directory

Each model is self-contained, and the same seven things are always present:

| Path | What it is | Who writes it |
|---|---|---|
| `model.py` | the model, in the Python DSL | you |
| `build/schema.pir`, `build/model.pir`, `build/product.pir` | the same model in canonical `.pir` | `predictable build` |
| `build/spans.json` | the Python ↔ `.pir` span map (`02-dsl.md` §8) | `predictable build` |
| `base.pir` | the assumption set | you |
| `run.pir` | the run configuration: modelpoints, `emit`, aggregations, solves | you |
| `tables/*.csv`, `data/modelpoints.csv` | the fixtures | `make_fixtures.py` |
| `expected/` | the goldens | `predictable run` + `goldens.py` |

Both representations are committed on purpose. The `.pir` is what the engine actually runs
and what `model_digest` is computed over; the Python is what a human edits. A test asserts
they have not drifted:

```console
$ python models/tools/regen.py            # regenerate everything
$ pytest models/tests -q                  # prove the committed files reproduce
```

### The goldens

| File | Question it answers |
|---|---|
| `summary.json` | the six reproducibility digests, the row and component counts, the solve outcome |
| `per_mp.csv` | every `PerMP` output for every modelpoint — the valuation result |
| `series_<key>.csv` | every `Series` output for one modelpoint, one row per `t` |
| `aggregates.csv` | the `[[aggregation]]` output |
| `solve_<name>.csv` | the per-modelpoint solve: solved value, residual, iterations |

`results_digest` is the whole answer in 64 hex characters — if it matches, every number
matches. The CSVs exist so that when it *doesn't* match you can see where.

## 2. Common notation

| Symbol | Meaning | Component |
|---|---|---|
| `t` | projection period, from 0 | `t` |
| `y` | policy year, `t // p + 1` for `p` periods a year | `policy_year` |
| `x` | attained age | `age` |
| `q` | probability of death in the period | `qx` |
| `w` | probability of lapse/surrender in the period | `wx` |
| `l[t]` | policies in force at the start of period `t`, per policy sold | `num_pols_if` |
| `v[t]` | discount factor to time 0 | `disc_factor` |
| `S` | sum assured | `sum_assured` |
| `P` | office premium | `premium_rate` / `monthly_premium` |

**Timing.** Every `Series` carries a timing tag — `start`, `end`, `mid` or `point` — and
adding two flows with different tags is a lint (`W0103`), not a silent approximation.
Premiums are `start` (in advance), claims are `end` (in arrears), balances are `point`,
and the net cashflow is explicitly restated to `mid` with `retime`.

**Decrement order.** All five models apply death first and lapse second within a period:

```text
l[t] = l[t-1] * (1 - q[t-1]) * (1 - w[t-1])
```

so the two decrements do not compete for the same exposure. Deaths in the period are
`l[t] * q[t]`; surrenders are `l[t] * (1 - q[t]) * w[t]`.

## 3. `term_annual`

**Product.** Level term assurance. Level sum assured payable on death within the term,
nothing on survival. Annual premium payable in advance for the whole term.

**Basis.** 40 annual periods, policy-year origin, valuation date 2026-06-30, flat valuation
rate 3.5%, mortality 105% of the base table, expenses inflating at 2.8% p.a.

**Portfolio.** 25 policies on a lattice of five entry ages (28–56), five terms (10–30
years), both sexes and both smoker statuses — every combination of interest exactly once,
none of them sampled.

### Formulas

Attained age and status:

```text
x[t]       = x0 + t
in_term[t] = t < n
```

Rates, from the tables:

```text
q[t] = mortality(x[t], sex, smoker) * mortality_loading
w[t] = lapses(y[t])                 * lapse_loading
```

Cashflows, all per policy sold:

```text
premium[t]  = P[t] * l[t] * [t < n]                    (start)
claims[t]   = S * l[t] * q[t] * [t < n]                (end)
expenses[t] = e * (1+j)^t * c_b * l[t] * [t < n]       (start)
```

`e` is the per-policy renewal expense, `j` the expense inflation, `c_b` the band scaling
from `tables/expenses.csv`, and `[cond]` an indicator that is 1 when `cond` holds.

Discounting is written as a recursion rather than a power, so that replacing the flat rate
with a term structure is a one-line change:

```text
v[t] = v[t-1] / (1 + i),   v[0] = 1
```

Best estimate liability, prospective, at issue:

```text
pv_claims   = sum_t v[t] * claims[t]
pv_expenses = sum_t v[t] * expenses[t]
pv_premiums = sum_t v[t] * premium[t]

bel = pv_claims + pv_expenses + initial_expense - pv_premiums
```

`initial_expense` is the acquisition expense, a percentage of the first premium.

The reserve is a **retrospective** roll-forward seeded from that prospective value:

```text
V[0] = bel
V[t] = (V[t-1] + premium[t-1] - claims[t-1] - expenses[t-1]) * (1 + i) * [t <= n]
```

!!! note "Why the reserve is retrospective"
    A prospective reserve at time `t` is a present value of *future* cashflows, which
    needs a backward recursion in `t` — and the IR forbids referring to `t+1`
    (`01-ir.md` §3.1). The retrospective form is the same quantity computed forwards, and
    it needs the prospective value only once, at `t = 0`. That single link is the one
    legal backward channel from stage 2 into stage 1 (`01-ir.md` §8.2), spelled
    `init = bel` in the DSL. It is used by four of the five reference models and it is
    worth learning.

    A consequence worth reading off the goldens: because the office premium contains a
    margin, `V[t]` does **not** run off to zero. At `t = n` it is the accumulated profit of
    the contract, and the model zeroises it after the term.

### Worked example

`TA00001`: male, smoker, entry age 28, sum assured 50 000, office premium 151.39, ten-year
term, expense band 1.

| Quantity | Value |
|---|---|
| `pv_premiums` | 920.46 |
| `pv_claims` | 217.49 |
| `pv_expenses` | 275.39 |
| `initial_expense` | 204.38 |
| **`bel`** | **−223.20** |
| `profit_margin` | 0.242 |

Read it as: the contract is worth 223.20 as an asset at issue, and the margin is 24% of the
present value of premiums. The first three projection years:

| `t` | `premium_income` | `death_claims` | `renewal_expenses` | `reserve` |
|---|---|---|---|---|
| 0 | 151.39 | 32.11 | 40.80 | −223.20 |
| 1 | 129.36 | 28.27 | 35.84 | −149.78 |
| 2 | 116.60 | 26.32 | 33.21 | −87.49 |

The premium falls from year to year because it is *per policy sold*: the survivorship
`l[t]` is already in it. The reserve climbs towards zero and then past it as the margin
emerges.

## 4. `term_monthly`

The same product, the same portfolio file, the same tables — projected monthly over 480
periods. It exists to make the consequences of a basis change explicit and to give the
benchmark a scenario whose cost is dominated by the `t` loop.

Four things change, and nothing else does:

1. **Attained age steps annually, not monthly.** `x[t] = x0 + y[t] - 1`, using the
   `policy_year` timeline input. Within a policy year the monthly and annual models read
   the *same* row of the mortality table.
2. **Rates convert on a constant force of decrement**: `q_m = 1 - (1 - q_a)^(1/12)` and
   `w_m = 1 - (1 - w_a)^(1/12)`. The uniform-distribution-of-deaths alternative `q_a / 12`
   is a materially different number at high ages; it is not used, and a model that wants it
   changes one line.
3. **The interest basis converts the same way**: `i_m = (1 + i)^(1/12) - 1`.
4. **Term is in years, `t` is in months**: in-term is `t < 12n`, and the premium is `P / 12`
   with no fractional-premium loading.

### The cross-check that matters

The two models are not equal and should not be — premiums are spread through the year
rather than paid up front, and claims fall on average half a year earlier — but they must
tell the same story. For `TA00001`:

| | annual | monthly |
|---|---|---|
| `pv_premiums` | 920.46 | 875.30 |
| `pv_claims` | 217.49 | 213.88 |
| `bel` | −223.20 | −191.57 |

The present values move by about 5%; the BEL, being a small difference between large
present values, moves by more. `models/tests` asserts the PVs agree within 10%, that the
BEL difference is within 10% *of the premium base*, and that the ranking of the portfolio
by liability is unchanged. Comparing the BELs to each other on a relative tolerance would
be the wrong test, and the test file says so.

## 5. `savings_monthly`

**Product.** Unit-linked endowment. Regular monthly premium for the whole term, allocated
to an account at a rate that is lower in the first policy year. Benefits:

* **death** — `max(S, AV)`;
* **surrender** — `max(AV * (1 - penalty(y)), 0)`;
* **maturity** — `max(AV, G)`, with `G` a guaranteed proportion of premiums paid.

**Basis.** 360 monthly periods. Four table lookups per policy per month: mortality, lapse,
surrender penalty, and a spot yield curve.

### The account value

The order of operations within the month is fixed and visible, because changing it changes
the answer:

```text
AV[t] = (AV[t-1] + alloc[t-1] * P - C[t-1]) * (1 + r_m)
```

allocate, then charge, then credit. The charges `C[t]` are three named components:

```text
cost_of_insurance[t] = max(S - AV[t], 0) * q[t] * coi_loading
management_charge[t] = AV[t] * (1 - (1 - amc)^(1/12))
policy_fee[t]        = f * (1 + j)^(y[t] - 1)

C[t] = cost_of_insurance[t] + management_charge[t] + policy_fee[t]
```

The **sum at risk** `max(S - AV[t], 0)` is the reason this model is in the corpus: it is a
branch evaluated for every policy in every month, and it is what `Select` with static trap
masking (`03-engine.md` §3.3) exists to make branch-free.

### Discounting off a curve

Unlike the term models, this one discounts on a term structure read from a table each
period rather than a flat-rate recursion:

```text
v[t] = (1 + spot(y[t]))^(-t/12)
```

That is deliberate: the corpus should contain one model whose discount factor is a lookup
and one whose discount factor is a recursion, because they lower to very different tapes.

### The guarantee

`pv_guarantee_cost` is the present value of `max(G - AV, 0)` paid at maturity, on the
central assumption set. It is a **deterministic** valuation of an option — the value of the
guarantee if the world does exactly what the assumptions say — not a stochastic one, and it
is the single number in the corpus most worth running a sensitivity fan over. On the
committed basis it bites on 3 of the 20 policies.

### Worked example

`SV00001`: male, smoker, entry age 30, 100 a month, ten-year term, sum assured 25 000,
guarantee 105% of premiums paid.

| Quantity | Value |
|---|---|
| `pv_premiums` | 7 052.69 |
| `pv_death_claims` | 118.69 |
| `pv_surrender_claims` | 1 278.65 |
| `pv_maturity_claims` | 4 641.49 |
| `pv_expenses` | 266.60 |
| `pv_guarantee_cost` | 326.60 |
| **`bel`** | **−387.26** |

The maturity claim dominates, as it should for a savings contract: this is a fund with a
small amount of insurance attached, not the other way round.

## 6. `ifrs17_gmm`

**Product.** The `savings_monthly` contract, unchanged. Everything above the `IFRS 17`
banner in `models/ifrs17_gmm/model.py` is that model verbatim; everything below it is the
general measurement model laid on top.

### Why this model is structurally different

IFRS 17 asks for quantities that depend on the *whole* projection and are then released
*over* the projection. The IR refuses to close that loop in one stage, so it is expressed
as the legal backward channel used twice:

```text
stage 1   fulfilment cash flows, coverage units          a Series
stage 2   their present values                           level 1  (an Agg)
stage 1   balances seeded from those values via `init`   CSM, RA, FCF roll-forwards
stage 2   present values of what those balances released level 2  (an Agg)
```

That second stage-2 pass is what `03-engine.md` §5.3's **substage levelling** exists for,
and this model is the corpus's test of it: two levels, no more. A model that needed a third
would be lint `W0110`.

### Measurement

**Fulfilment cash flows.** `FCF = bel`, as in §5.

**Risk adjustment.** A percentage loading on the present value of claims:

```text
RA = ra_pct * (pv_death_claims + pv_surrender_claims + pv_maturity_claims)
```

This is a confidence-level-free proxy, chosen because it is auditable in one line. A
cost-of-capital or quantile calibration replaces exactly this component and nothing else.

**Contractual service margin at initial recognition.**

```text
CSM[0] = max(-(FCF + RA), 0)
LC[0]  = max( (FCF + RA), 0)
```

A contract has one or the other and never both. `is_onerous` reports which.

**Coverage units.** Sum assured in force, per 1000: `CU[t] = l[t] * S / 1000`, discounted
to `t = 0` as `CUd[t] = CU[t] * v[t]`. Coverage units
are a policy choice under IFRS 17.B119; sum assured in force is used because the benefit is
a death benefit, and swapping the definition is a one-line change that the model diff
classifies as a formula change to this component alone.

**Release.** Both the CSM and the RA release on the same fraction of remaining service:

```text
R[0]       = sum_t CUd[t]                                    # total_coverage_units
R[t]       = max(R[t-1] - CUd[t-1], 0)                       # remaining_coverage_units
phi[t]     = min(CUd[t] / max(R[t], 1e-9), 1)                # release_fraction
CSM[t]     = max((CSM[t-1] - release[t-1]) * (1 + i_lock_m), 0)
release[t] = CSM[t] * phi[t]
```

`R[0]` is a stage-2 sum reaching stage 1 through `init` — level 1. The present value of
`release[t]` is then a stage-2 sum over a series that was itself seeded that way — level 2.

**Balances.** The FCF balance rolls forward exactly like `term_annual`'s reserve, and

```text
LRC[t] = FCF[t] + RA[t] + CSM[t]
```

**The identity.** For a profitable contract `CSM[0] = -(FCF[0] + RA[0])`, so

```text
LRC[0] = FCF[0] + RA[0] + CSM[0] = 0
```

No gain is recognised at initial recognition. For an onerous contract there is no CSM and
`LRC[0] = LC[0]`, the loss recognised immediately. `lrc_at_issue` is that check, published
as an output so a run can be reconciled without opening the model, and asserted in
`models/tests`.

**Profit or loss.** Insurance revenue less insurance service expense is, on the central
assumptions, exactly what the two balances released:

```text
insurance_service_result[t] = ra_release[t] + csm_release[t]
```

which is also a test.

### Worked example

`SV00001`, the same policy as §5:

| Quantity | Value |
|---|---|
| `bel` (FCF) | −387.26 |
| `risk_adjustment` | 271.75 |
| `csm_initial` | 115.51 |
| `loss_component_initial` | 0.00 |
| **`lrc_at_issue`** | **0.00** |
| `total_coverage_units` | 1 763.17 |
| `pv_csm_release` | 118.89 |
| `pv_ra_release` | 279.69 |
| `pv_insurance_service_result` | 398.58 |

`-(-387.26 + 271.75) = 115.51` — the CSM. The LRC at issue is zero to the last bit. And
the profit recognised over the contract, 398.58, is the CSM plus the risk adjustment
released, both discounted.

On the committed basis the 20-policy portfolio splits 11 profitable / 9 onerous, which is
deliberate: a corpus in which every contract is profitable never exercises the loss
component, and one in which every contract is onerous never exercises the CSM.

## 7. `term_solve`

`term_annual`, with a `[[solve]]` block. **The model file is byte-for-byte the same** —
`models/term_annual/expected/summary.json` and `models/term_solve/expected/summary.json`
carry the same `model_digest` and different `run_digest`. That is the situation a run diff
has to attribute to the configuration rather than to the model, and it is why the two
directories exist rather than one.

```toml
[[solve]]
name      = "breakeven_premium"
target    = "bel"
to        = 0.0
vary      = "annual_premium"
scope     = "per_mp"
tolerance = 1e-8
max_iter  = 60
method    = "brent"
bracket   = [1.0, 100000.0]
```

For each modelpoint, vary the office premium until the BEL is zero: the break-even, or
zero-margin, premium. The projection itself stays a pure function of its inputs — the
solver sits strictly outside it (`01-ir.md` §8.4.4).

Results land in two places. `solves/breakeven_premium.parquet` carries the solve's own
evidence, and the solved value is *also* materialised as an ordinary `PerMP` component so
downstream joins do not have to special-case it:

| `mp_key` | `solved_value` | `residual` | `iterations` | `converged` |
|---|---|---|---|---|
| TA00001 | 104.202120 | −3.4e−13 | 3 | true |
| TA00002 | 102.445715 | 0.0 | 3 | true |

All 25 modelpoints converge, in three iterations each, to a maximum absolute residual of
2.7e−12. `TA00001`'s office premium is 151.39 against a break-even of 104.20, which is the
24% margin of §3 seen from the other side.

The consistency test worth knowing: a policy whose BEL is negative in `term_annual` must
solve to a premium *below* its office premium, and a policy whose BEL is positive must
solve to one above it. A solver converging to the wrong root, or varying the wrong input,
breaks that immediately.

## 8. Portfolio aggregation

Every run declares `[[aggregation]]` blocks, so the corpus exercises the monoid stage as
well as the projection:

| Model | Aggregations |
|---|---|
| `term_annual`, `term_solve` | `bel_by_sex` (sum), `net_cashflow_by_band` (sum, per `t`) |
| `term_monthly` | as `term_annual` |
| `savings_monthly` | `bel_by_sex`, `net_cashflow_by_cohort` |
| `ifrs17_gmm` | `csm_by_cohort`, `insurance_service_result_by_cohort` |

Group keys are rendered `key=value` in `group_by` order and are stable join keys. Partials
combine in chunk-index order, never in completion order, so `aggregates.parquet` is
identical under any chunk size or thread count — which `models/tests` asserts directly.

## 9. Reproducing and extending

```console
# regenerate fixtures, .pir builds, runs and goldens for all five models
$ python models/tools/regen.py

# or just one
$ python models/tools/regen.py ifrs17_gmm

# prove the committed corpus reproduces
$ pytest models/tests -q
```

To add a sixth model: create `models/<name>/` with `model.py`, `base.pir` and `run.pir`,
add the name to `MODELS` in `models/tools/regen.py`, teach `make_fixtures.py` to write its
tables and modelpoints, and run `regen.py`. The tests are parametrised over `MODELS`, so
the new model is covered by the structural, drift, golden and determinism tests the moment
it is listed. Its actuarial identities belong in `models/tests/test_reference_models.py`
next to the others.

### Two things to know before you rely on these numbers

**Enum-keyed tables are avoided.** `sex` is carried as `str`, not as an `enum(Sex)`, in
every model. An `enum` modelpoint field used as a table key does not currently resolve at
runtime — the lane carries a schema variant index where the compiled table expects an
engine dictionary code — so a lookup keyed on one misses. `str` keys work correctly and are
what the corpus uses until that seam is closed.

**`results.parquet` bytes are not yet chunk-size invariant on the larger models.** Every
*value* is identical under `--chunk-size 1` and `--chunk-size 4096`, and so is
`aggregates.parquet`; the Parquet encoding of the results file is not, so `results_digest`
moves. `models/tests` asserts the value-level invariant strictly and carries the byte-level
one as an expected failure with the reason attached.

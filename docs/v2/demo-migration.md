# Demo: migrating a Prophet library

The migration demo is a **real, executed** migration of an FIS Prophet library into
predictable, reconciled to the penny against the Prophet run it came from, with the whole
loop recorded.

```console
$ ./demos/migration/run_demo.sh
...
MIGRATION DEMO: OK
```

The full annotated transcript — every command, every diff, every diagnostic — is
[`demos/migration/README.md`](https://github.com/RatulMaharaj/predictable/blob/main/demos/migration/README.md).
This page is what the demo is *for*, and what to watch while it runs.

Related reading: [the migration skill](migration-skill.md) drives it,
[reading Prophet files](prophet-readers.md) is what parses the workspace,
[diffing two runs](run-diff.md) and [hypotheses](hypotheses.md) are what localise the
errors, and [the verification loop end to end](verification-walkthrough.md) is the same
machinery rehearsed against two predictable runs instead of against Prophet.

---

## The claim

> An agent can take a Prophet library, reimplement it in predictable, and **prove** the
> reimplementation right — rather than assert it.

The proof is the deliverable. A model that produces plausible numbers and cannot be
reconciled is not a migration; it is a second opinion.

## The setup, and why it is honest

`TERM_UK` is a synthetic Prophet library — `.MOD` source, `.mpf` model points, three `.fac`
tables and a `.rpt` results file — generated by
`demos/migration/tools/make_prophet_run.py`. That generator's `project()` function is a
plain-Python transcription of the `.MOD` file written against the `.MOD` text and nothing
else: no predictable import, no shared code.

So when the two agree at the end, it is because **two independent implementations of one
specification agree**, which is the only version of that claim worth making. The `.rpt` is
written the way Prophet writes one — periods from 1, money to two decimals — because the
half-penny rounding is exactly what the `reconcile` tolerance profile exists to absorb.

## What to watch

### Iteration 1 diverges, and the differ does the triage

The first translation checks clean and is wrong in two places: `qx` forgets the mortality
loading (which lives in the Prophet *run settings*, not in the `.MOD` file, which is why it
gets missed), and renewal expenses inflate from `t + 1` instead of `t`.

```text
DIVERGED   2,863 of 6,560 cells   3 root divergences   7 outputs affected
```

**Nine** components diverge; **three** are roots and six are `inherited` — the same error
seen further downstream, which disappears when its root is fixed. Fixing inherited findings
one at a time is how a migration takes three weeks.

### The hypothesis names the bug

```text
▸ F003  root   qx
    H0101  (high confidence, held on 15/15)  b/a is constant at 0.952380952 across all 41
           periods of `qx`: a scale factor, not a behavioural difference
        suggested edit  build_iter1/model.pir:806..836
        - "mortality@(age, sex, smoker)"
        + "(mortality@(age, sex, smoker)) * 1.0499999999999998"
```

`0.952380952 = 1 / 1.05`. The differ never read the Prophet run settings and does not know
`MORT_LOAD` exists — it inferred a constant ratio from the numbers, checked that the claim
held on every sampled model point, and proposed the reciprocal as a byte-anchored edit.

A *constant ratio* is a much narrower class of bug than "the numbers are off", and saying
which class it is, with the evidence, is the difference between a diff and a diagnosis.

### Iteration 2 reconciles, and nothing was loosened

```text
MATCHED   0 of 6,560 cells   0 root divergences
```

`max |a − b| = 0.0` across 16 model points × 41 periods × 10 mapped components.
`tolerance.loosened = 0`; `mapping.adjusted = []` — no `sign`, no `scale`, no
`timing_shift` was declared, so the mapping asserts nothing about Prophet's conventions
beyond the correspondence of names and the period base.

The one hard prohibition of the skill is that a tolerance is never widened to silence a
finding: it converts an unexplained difference into an invisible one. The demo asserts
that it was not.

## Where predictable and Prophet genuinely differ

Two translations in the demo are not spelling changes:

**Timing is a decision, not a default.** Prophet has no timing tags; whether a claim falls
at the start or the end of the policy year lives in the modeller's head and in the
discounting. predictable requires `timing=` on every series, so it is decided once,
visibly — and `npv` then discounts an `END` flow one period further than a `START` flow
automatically. In the `.MOD` file that shows up as a `DISC(t+1)` you have to remember; here
it is a consequence of a tag you could not omit.

**`LAPSE_TERM(t + 1)` becomes `lapses(policy_year)`.** Prophet indexes the table with
arithmetic on `t`. `policy_year` is a timeline builtin, and using it is what stops the key
silently drifting if the model is ever re-based to monthly.

## The stop condition

`skills/predictable-migration` step 7 is four booleans, and `run_demo.sh` asserts all four
plus thirteen more:

| condition | how it is checked |
|---|---|
| `verdict = "matched"` at the `reconcile` profile | `migration/diff_final.json` |
| every Prophet variable mapped, derived or declared out of scope | `migration/coverage.json` — 10 / 9 / 1 |
| `check` clean of errors and `W0102` unit lints | `3 file(s) checked, no diagnostics` |
| no tolerance widened | `tolerance.loosened = 0`, `mapping.adjusted = []` |

## What is not claimed

`TERM_UK` is 20 variables. The skill's success metric is a ~50-variable library in under an
hour of agent time, and this demo is deliberately smaller — sized to be *auditable in one
sitting*, so a reader can check the `.MOD` file against `model.py` line by line, rather than
sized to be impressive. Nothing here exercises the constructs the readers refuse to guess at
(ambiguous dates `P0109`, table orientation `P0202`); a real library will hit them, which is
what `references/prophet-idioms.md` is for.

# 01 — The predictable IR

Status: **normative**. Version: IR `1.0` (format `pir/1`).
Audience: engine implementers (Rust), DSL implementers (Python), and LLMs writing/reading models.

The IR is the contract between the Python authoring DSL and the Rust projection engine. It is
the *only* thing the engine executes. It is a file on disk, in git, reviewable in a pull request.
Everything else — the DSL, the CLI, the web UI, `explain()`, run-diff — is a producer or consumer
of this artifact.

Three hard rules, from which most of this document follows:

1. **No arbitrary code crosses the boundary.** No Python lambdas, no `eval`, no plugin callbacks
   during projection. Every formula is data: a typed expression tree.
2. **The text form is the source of truth.** Not a serialisation of an in-memory object graph that
   happens to round-trip. The engine parses the text; the DSL emits the text; a human or an LLM may
   write the text by hand and it will run.
3. **The IR is total and checkable before execution.** Every error that can be raised at
   definition time must be raised at definition time, with a span, a message, and a fix.

---

## 1. Vocabulary

Carried forward from v0 and from Prophet, deliberately:

| Term | Meaning | Prophet analogue |
|---|---|---|
| **component** | A named, typed node in the computation graph. The unit of definition, of results, of diffing. | variable |
| **modelpoint** | One policy / record being projected. | model point (MPF row) |
| **modelpoint field** | A typed column of the modelpoint file, readable as an input. | `MP_Field` |
| **table** | An external keyed lookup: mortality, lapse, expense inflation. | `.fac` table |
| **assumption** | A named scalar or table-valued run input, versioned separately from the model. | run setting / parameter file |
| **run** | Model + assumption set + modelpoint file + run config → results. | run |
| **projection** | The `t = 0..T` evaluation for one modelpoint. | projection |
| **module** | A namespaced file of components. | library / workspace |
| **product** | A named entry point: a set of modules plus the output component list. | product |

`t` is always an integer period index, `0..=T`. `t` is *not* a date; the mapping to dates is a
property of the timeline (§5).

## 2. Data model

### 2.1 Component

A component is:

```
component := {
  name:        Ident                    -- unique within its module
  kind:        Kind
  dtype:       DType
  shape:       Shape
  unit:        Unit
  timing:      Timing                   -- only for shape = Series
  expr:        Expr                     -- the formula (absent for inputs)
  init:        Option<Expr>             -- value at t = 0 for recursive series
  meta:        Meta                     -- doc, tags, source span, provenance
}
```

### 2.2 Kind

```
Kind ::= Input.Modelpoint     -- read from the modelpoint file
       | Input.Assumption     -- read from the assumption set
       | Input.Table          -- an external table declaration
       | Input.Timeline       -- t, month_of_year, year, period_start_date, ...
       | Derived              -- computed from an Expr
       | Output               -- Derived, additionally marked for results emission
```

Inputs have no `expr`. `Output` is `Derived` plus an emission flag; it exists so that the results
schema is a property of the model, not of the run.

**There is no `Kind::Abstract`** (Q10). "Declared but undefined" is a DSL/build-time concept only: the
DSL's `@abstract` marker is discharged by an `@override` in a concrete product, and an undischarged
abstract fails `predictable build` with `E1203` *before* any `.pir` is written. Every component in a
well-formed `.pir` file has either a `kind` of `Input.*` or an `expr`. A hand-written `.pir` therefore
never contains a hole, and the resolve pass (§7 pass 2) needs no "pending definition" state.

**`Output` is the single source of truth for emission** (Q2). A `[product]` block (§8.4.1) may list
`outputs`, but that list is a *validated manifest*, not a selector: the checker requires it to equal
the set of `kind = "Output"` components reachable from the product's modules, and reports `E0107`
("product output list disagrees with the model") on mismatch. Nothing selects outputs at run time
except `run.emit` (§8.4.2), which only ever *widens* the emitted set.

There is no `Aggregate` *kind*. Reduction over `t` is a property of the **expression** (an `Agg`
node, §2.6), which makes the component stage-2 (§8.2); its kind stays `Derived` or `Output`. `stage`
is therefore a *computed* field — `2` iff the component's `expr` contains an `Agg`, else `1` — and it
is exposed on every component in `pir.json`, in `GraphDoc` (`05-viz.md` §2.1) and in the results
schema (`04-verify.md` §2), so consumers never re-derive it.

**Component identity.** A component's canonical fully-qualified id is `<module_path>.<name>`, with
`module_path` dot-separated (`term_assurance.decrements.num_pols_if`). Unqualified names are globally
unique within a product (cross-module shadowing is an error, §7 pass 2), so the qualified form is
presentational and join-stable rather than disambiguating. It is the join key in results, traces,
run-diffs and mapping files, and it is normative: no other separator is legal.

### 2.3 Shape — the three-way distinction

This is the core of the data model. Every component has exactly one of:

```
Shape ::= Scalar     -- one value for the whole run.        e.g. valuation_rate
        | PerMP      -- one value per modelpoint.           e.g. entry_age, sum_assured
        | Series     -- one value per modelpoint per t.     e.g. premium[t], reserve[t]
```

There is deliberately no "per-t but not per-modelpoint" shape. A yield curve indexed by `t` alone
is a `Series` whose expression happens not to reference any `PerMP` component; the engine's
loop-invariant analysis hoists it and computes it once per run, but the *model* sees a uniform
`Series`. This keeps the type lattice at three points and keeps formulas free of broadcast syntax.

**Broadcast rules** (the only implicit coercion in the IR):

```
Scalar ⊔ Scalar = Scalar
Scalar ⊔ PerMP  = PerMP
Scalar ⊔ Series = Series
PerMP  ⊔ PerMP  = PerMP
PerMP  ⊔ Series = Series
Series ⊔ Series = Series
```

Widening is implicit and free. **Narrowing is never implicit.** Going from `Series` to `PerMP`
requires an explicit `Agg` (`sum`, `npv`, `at`, `first`, `last`, `max_over`, `min_over`, `count_while`).
Going from `PerMP` to `Scalar` requires an explicit portfolio-level aggregate, which is a *run-level*
construct and is not expressible inside a projection (§8.3).

### 2.4 DType and Unit

```
DType ::= f64 | i64 | bool | date | str | enum(<EnumName>)
```

`f64` is the only arithmetic float type. There is no `f32`, no decimal: see §9.

`Unit` is a lightweight dimensional tag, checked but not converted:

```
Unit ::= none                      -- pure number
       | money                     -- a currency amount; currency is a run property
       | rate(basis)               -- basis ∈ { annual, monthly, period }
       | prob                      -- in [0,1], dimensionless probability
       | count | years | months | factor
```

Unit checking is intentionally shallow — it catches the errors actuaries actually make:

- `money + prob` → error.
- `rate(annual) + rate(monthly)` → error. ("Rates on different bases cannot be added. Convert with
  `to_monthly(x)` or set the component's basis explicitly.")
- `money * prob` → `money`. `money * money` → error.
- `money / money` → `factor`. `prob * prob` → `prob`.
- `1 - prob` → `prob`. Literals are unit-polymorphic and unify with their context.

`unit = "none"` on a component opts out; it is legal and sometimes right, but the DSL emits a lint.

### 2.5 Timing

`Series` components carry a timing tag describing *when within period `t`* the value is realised:

```
Timing ::= start      -- in advance: at the beginning of period t (premiums, in-advance annuities)
         | end        -- in arrears: at the end of period t (claims paid, interest credited)
         | mid        -- uniformly / mid-period (a common claims approximation)
         | point      -- a state measured at an instant, not a flow (reserve, in-force count)
```

Timing is *not* decoration. It is consumed by:

- **Discounting.** `npv(x)` uses the timing of `x` to pick the exponent on the discount factor:
  `start` → `v^t`, `end` → `v^(t+1)`, `mid` → `v^(t+0.5)`, `point` → `v^t`.
  This removes the single most common off-by-one-period error in hand-rolled models.
- **Aggregation lints.** Adding a `start` flow to an `end` flow is a warning, not an error, with
  the fix `shift(x, 1)` or an explicit `retime(x, end)`.
- **`explain()`**, which shows the timing of every node in a trace.

`retime(x, timing)` is a no-op on values and a cast on the tag; it is the escape hatch and it is
visible in the diff.

**Timing on non-`Series` values** (Q14). `Scalar` and `PerMP` components have no timing; their
`timing` field is absent in `.pir` and serialises as `null` in `pir.json`. The result of an `Agg` —
`npv(x, v)`, `sum(x)`, `last(x)` — is a `PerMP` and is therefore **untimed**: the timing of `x` has
already been consumed by the reduction. This is a lint, not a semantic change:

```
warning[W0105]: `retime` on a value that has no timing

  `npv(premium_income, disc_factor)` is a PerMP; its timing was consumed by the
  discounting, so retiming the result changes nothing.

   ┌─ reserves.pir:22:8
22 │ expr = "retime(npv(premium_income, disc_factor), end)"
   │         ^^^^^^ this call has no effect

  If you meant to change the discounting exponent, retime the flow instead:

22 │ expr = "npv(retime(premium_income, end), disc_factor)"
```

`W0105` fires for `retime`, `shift`, `cum` and `diff` applied to a `Scalar` or `PerMP` operand. Each
is a well-defined no-op (identity for `retime`/`cum`, identity for `shift`, zero for `diff`), so the
model still runs — but the author almost certainly meant to apply it one level down.

### 2.6 Expressions

```
Expr ::= Lit(value, dtype)
       | Ref(name)                          -- current period / current modelpoint
       | Lag(name, k)                       -- name[t-k], k >= 1
       | At(name, k)                        -- name[k], absolute index, k >= 0
       | Unary(op, Expr)
       | Binary(op, Expr, Expr)
       | If(cond: Expr, then: Expr, else: Expr)
       | Call(fn, [Expr])                   -- builtin only; see §2.8
       | Lookup(table, [key: Expr])         -- table lookup
       | Agg(op, Expr, Option<Expr>)        -- reduction over t, optional predicate
```

Notably absent: user-defined functions, loops, mutable state, lists, dictionaries, string
manipulation beyond equality, and anything that can fail to terminate. An `Expr` evaluates in
bounded time proportional to its own size.

`If` is a *value* conditional and evaluates both branches; there is no short-circuit control flow.
Division by zero and out-of-range lookups are the only trapping operations (§9.3).

**Trap suppression in untaken arms.** A trap raised inside an `If` arm is suppressed when that arm is
not taken. The mask is derived **syntactically** from the enclosing chain of `If` conditions — there
is no dynamic predicate stack and no data-dependent control flow. This makes
`if x == 0 then 0.0 else 1.0 / x` legal and correct, which it must be: it is the most common
defensive idiom in actuarial code. Values in a suppressed arm are unspecified and unobservable; they
never reach a result, and `explain()` records the arm as `"suppressed": true`.

### 2.7 Time references — `Ref`, `Lag`, `At`

Inside a `Series` component's expression:

- `x` (a `Ref`) means `x[t]` — the value of `x` in the *same* period.
- `x[t-1]` (a `Lag` with `k = 1`) means the previous period. `k` may be any positive integer literal.
- `x[0]`, `x[12]` (an `At`) means an absolute period. `At` is how you reference issue-time values of
  something that varies over time.
- Forward references — `x[t+1]`, `x[T]` — are **illegal**. A projection is a single forward pass.
  Backward-looking recursion is expressible; forward-looking is not. If you need a value that
  depends on the future (a retrospective-to-prospective reserve check, an IFRS 17 CSM unlock over a
  full projection), you express it with an `Agg` over the completed series, which is evaluated in a
  second pass (§8.2).

**Out-of-range semantics** are fixed and not configurable:

- `x[t-k]` for `t - k < 0` evaluates to `x`'s **`init`** if the component declares one; otherwise to
  the zero of its dtype (`0.0`, `0`, `false`) — and the engine records a `pre_origin_default` note
  in the provenance so `explain()` can show it. `date` and `str` have no zero: a `Lag` on them
  without an `init` is a definition-time error.
- `x[k]` for `k > T` is a definition-time error when `k` is a literal and `T` is known from the run
  config; otherwise a trap at `t = k`.

### 2.8 Builtin function set

Closed. Adding to it is an IR minor-version bump (§10). Version 1.0:

```
arithmetic   min max abs floor ceil round(x, dp) clamp(x, lo, hi) sign
exp/log      exp ln pow(x, y) sqrt
rates        to_monthly(r) to_annual(r) nominal_to_periodic(r, n) v_from_i(i) i_from_v(v)
             annuity_factor(i, n) compound(r, n)
timing       shift(x, k) retime(x, timing) cum(x) diff(x)
logic        and or not eq ne lt le gt ge is_null coalesce(x, y)      -- is_null/coalesce: see §2.11
dates        year month day add_months(d, n) months_between(a, b) year_frac(a, b, convention)
aggregates   sum sum_kahan npv(x, disc) first last at(x, k) max_over min_over count_while(cond)
```

`npv(x, disc)` takes a discount-factor `Series`, not a rate, and uses `x`'s timing tag (§2.5).

`nominal_to_periodic(r, n)` is `r / n` — simple division, named so the choice is visible in the diff.
It is the sanctioned escape hatch from §5's basis-conversion rule and the one the `E1402` message
offers.

`round(x, dp)` is **round-half-away-from-zero on the shortest decimal representation of `x`**, not
IEEE round-half-even: it matches Prophet and actuarial convention. This is a semantic property;
changing it is a major bump. Implementation guidance and the `2.675` trap are in `04-verify.md` §5.6.

`count_while(cond)` **stops at the first `t` where `cond` is false** and returns that count; it does
not count all true periods. `at(x, k)` (aggregate) and `x[k]` (the `At` expr node, §2.6) are the same
operation — `at` is the call spelling for use where an infix index is awkward, and both lower to
`At`.

`and`/`or`/`not` appear in the grammar (§4.2) as infix/prefix operators; the names in this table are
their node-level identities. A producer that cannot write infix (the Python DSL, which cannot
overload `and`) emits the infix form: `all_(a, b, c)` lowers to `a and b and c`. There is no variadic
logic node.

### 2.9 Tables

A table is a declared input, not a file path buried in a formula (v0's mistake — see
`predictable/core/lookup.py`, where the CSV path was an attribute of the component and the join was a
pandas `join` with silent NaN):

```toml
[[table]]
name       = "mortality_sa8990"
keys       = [
  { name = "age",    dtype = "i64", policy = "clamp" },
  { name = "gender", dtype = "enum(Gender)", policy = "exact" },
  { name = "smoker", dtype = "bool", policy = "exact" },
]
values     = [{ name = "qx", dtype = "f64", unit = "prob" }]
on_missing = "error"           # error | default(<lit>) | interpolate(<key>)
source     = "tables/sa8990.csv"
digest     = "sha256:9f2c...e1"
```

- `keys` are ordered and typed. A `Lookup` supplies exactly one expression per key, in order.
- `policy` per key: `exact` (miss → `on_missing`), `clamp` (clamp to the table's key range),
  `step` (last value ≤ key, for banded tables), `interpolate` (linear, `f64`/`i64` keys only).
- `on_missing = "error"` is the default. Silent NaN propagation is not available at any setting.
- **Enums are unordered.** `enum(...)` key dtypes support `policy = "exact"` only; `clamp`, `step`
  and `interpolate` on an enum key are `E0305`. Declaration order in `[[enum]]` is presentational —
  it fixes the dictionary encoding for results, and reordering changes no computed value — so enums
  compare by equality alone and never by ordinal.
- `digest` pins the table content. A run whose table file digest differs from the IR's is refused
  unless `--allow-table-drift`, and the digest change appears in the git diff — table changes are as
  reviewable as code changes.

Tables are loaded once per run and are immutable during projection.

#### 2.9.1 `source` resolution and the `TableResolver` contract (Q5)

`source` is **always resolved relative to the directory containing the `.pir` file that declares the
table**, never relative to the process working directory, never relative to a project root. A
declaration is therefore relocatable with its file, and `models/term_assurance/schema.pir` declaring
`source = "tables/sa8990.csv"` means `models/term_assurance/tables/sa8990.csv`. Absolute paths and
any path escaping the *project root* (the nearest ancestor directory containing `predictable.toml`,
else the module's own directory) are `E0801`; this keeps a `.pir` file from reading arbitrary bytes
off the machine that checks it.

`source` may also be a URI with an explicit scheme, in which case the scheme selects the resolver:

```toml
source = "tables/sa8990.csv"                  # file, relative to the declaring .pir
source = "resource:sa8990"                    # supplied by the host, keyed by name
source = "inline"                             # rows carried in the .pir itself, see below
```

The engine never opens a file directly. It calls a resolver:

```rust
pub struct TableBytes { pub bytes: Vec<u8>, pub origin: String, pub format: TableFormat }

pub trait TableResolver {
    /// `decl` is the table declaration; `base` is the directory of the declaring .pir file.
    fn resolve(&self, decl: &TableDecl, base: &Path) -> Result<TableBytes, ResolveError>;
}
```

Three implementations are normative for 1.0:

| Resolver | Selected by | Behaviour |
|---|---|---|
| `FsResolver` | default, `file` scheme | reads `base.join(source)`, sandboxed to the project root |
| `MapResolver` | `resource:` scheme | looks the name up in a host-supplied `BTreeMap<String, Vec<u8>>` — this is what WASM, hosted runs and `predictable export` use; there is no filesystem in that build |
| `InlineResolver` | `source = "inline"` | reads the `[[table.rows]]` array in the declaration itself |

**The digest, not the path, is the table's identity.** Whatever the resolver returns is hashed and
compared to `digest` before compilation (§2.9); a mismatch is refused unless `--allow-table-drift`.
This is what makes the resolver swap safe: a `resource:` run and an `file:` run of the same model
either agree on the bytes or are told they do not. `run.tables` (§8.4.2) may override the `source` of
a named table for one run; it may never override the `digest`.

`inline` tables carry their content in the module and are what `predictable export` writes when
producing a self-contained governance pack:

```toml
[[table]]
name   = "lapse_rates"
keys   = [{ name = "policy_year", dtype = "i64", policy = "step" }]
values = [{ name = "lapse_pa", dtype = "f64", unit = "prob" }]
source = "inline"
digest = "sha256:31aa…"
rows   = [
  [1, 0.12],
  [2, 0.08],
  [3, 0.05],
]
```

`rows` is an array of arrays in `keys ++ values` order, sorted ascending by the key tuple. Its digest
is computed over the canonical text of the `rows` array, so an inlined table and its CSV original are
*not* required to share a digest; `predictable export` records both in `manifest.inputs.tables[]`
as `digest` and `declared_digest`.

### 2.10 Modelpoint schema

The modelpoint schema is part of the IR, not inferred from the data file. This is what makes an MPF
mismatch a definition-time error with a good message rather than a `KeyError` on row 40,000.

```toml
[[modelpoint_field]]
name = "sum_assured"
dtype = "f64"
unit = "money"
required = true
```

Optional fields must declare a `default`. Enum fields must declare their `enum`. A modelpoint file
with an unknown extra column is accepted with a lint; a missing required column is a hard error
naming the file, the column, and the components that reference it.

### 2.11 Nulls and missingness (Q3)

**There is no null value at runtime.** Every lane of every component holds a defined value of its
dtype for every `t`. There is no validity bitmap in the lane layout, no null rule on any operator,
and no three-valued logic. This is a deliberate, load-bearing decision: it is what keeps the kernel's
inner loop a dense `f64` scan and keeps `explain()` free of "this was null so the whole subtree is
null" cascades.

Missingness is eliminated **at the boundary**, in exactly two places:

1. **Optional modelpoint fields.** A field declared without `required = true` must declare a
   `default`. At load, a missing or null cell is replaced by the default. Rows are validated before
   projection starts, so no lane can ever contain a sentinel.
2. **Lookup misses.** `on_missing = "default(<lit>)"` substitutes the literal at compile time of the
   lookup structure. `on_missing = "error"` (the default) traps (§9.3). `interpolate` never misses
   inside the key range.

`is_null(x)` and `coalesce(x, y)` therefore do not observe a runtime null; they observe a **presence
bit**, and they are legal only where a presence bit exists:

- `is_null(f)` where `f` is a `Ref` to an **optional modelpoint field**. The loader materialises one
  `bool` `PerMP` presence lane per such field *only when the model actually calls `is_null`/`coalesce`
  on it* — the cost is opt-in and visible.
- `is_null(tbl@(k…))` where `tbl` has `on_missing = "default(…)"`. The lookup compiler emits the hit
  flag alongside the value for exactly those tables.

Anywhere else, `is_null` is `E0602` ("`x` can never be missing; `is_null` here is always false"),
with the suggested edit being deletion of the call. `coalesce(x, y)` is sugar for
`if is_null(x) then y else x` and inherits the same rule, including branch-dtype unification.

Consequences worth stating: `0.0 / 0.0` traps rather than producing a null (§9.3); a trapped
modelpoint under `--continue-on-trap` produces **no rows at all**, not null rows (§9.3.1); and the
results schema's nullable `value_*` columns (`04-verify.md` §2) express *dtype selection*, not
missing data.

## 3. The graph

Components form a directed graph. Edges are labelled with a **lag**:

```
edge := (from: ComponentId, to: ComponentId, lag: u32, via: ExprPath)
```

- A `Ref(x)` inside `y` creates edge `x → y` with `lag = 0`.
- A `Lag(x, k)` creates `x → y` with `lag = k`.
- An `At(x, k)` creates `x → y` with `lag = ∞` (a *seed* edge; see below).
- A `Lookup` creates edges from each key expression's refs, plus a dependency on the table.
- An `Agg(op, x)` creates a **whole-series** edge `x ⇒ y`, marked `stage = 2` (§8.2).

Two components may be joined by several edges (`reserve[t-1] + reserve[0]`); they are distinct edges,
distinguished by `via`, never coalesced. Consumers that want one arrow per pair (the graph explorer's
default zoom) merge on `(from, to)` themselves and keep `via` as the merged list.

### 3.0.1 `ExprPath` (Q9)

`via` is an **`ExprPath`**: a dotted, deterministic path from a component's expression root to the
`Ref`/`Lag`/`At`/`Lookup` node that produced the edge. It is a string; its grammar is:

```
exprpath := root ("." seg)*
root     := "expr" | "init"
seg      := "lhs" | "rhs"                 -- Binary
          | "operand"                     -- Unary
          | "cond" | "then" | "else"      -- If
          | "arg" INT                     -- Call, 0-based
          | "key" INT                     -- Lookup, 0-based
          | "value"                       -- Agg first operand
          | "pred"                        -- Agg optional predicate
```

Every segment names the *field* of the parent node, so a path is readable without the tree:
`expr.lhs.arg0.key1` is "the second lookup key of the first argument of the call on the left of the
top-level binary operator". Paths into `init` start with `init`, which is how `G_init` edges (§3.1)
are located. For

```toml
expr = "(reserve[t-1] + premium_income[t-1]) * (1 + valuation_rate)"
```

the four edges are `reserve → reserve` via `expr.lhs.lhs`, `premium_income → reserve` via
`expr.lhs.rhs`, `valuation_rate → reserve` via `expr.rhs.rhs`, and nothing else.

Rules: the path is derived from the **canonical** expression (§4.1), so `fmt` never changes one;
parentheses are not segments (they are not nodes); the empty path `"expr"` is legal and means the
whole expression is the reference (`expr = "bel"`). An `ExprPath` resolves to at most one node, and
`resolve(path)` returning `None` against the current model is how a consumer detects a stale cached
layout. `ExprPath` is byte-range-independent by design: spans move when the file is reformatted,
`ExprPath` does not.

### 3.1 Cycle rules — why `t-1` self-reference is legal

Define the **instantaneous subgraph** `G₀` = all edges with `lag = 0` and `stage = 1`.

> **Rule:** the model is valid iff `G₀` is acyclic. Edges with `lag ≥ 1` are unconstrained and may
> form cycles, including self-loops.

The intuition is standard for synchronous dataflow: within a single period, values must be
computable in some order; across periods, the previous period is already fully computed and is just
data. `reserve[t] = (reserve[t-1] + premium - claims) * (1 + i)` is a self-loop with `lag = 1`,
therefore legal. `a = b + 1; b = a + 1` is a two-cycle in `G₀`, therefore an error.

`At(x, k)` edges are the one subtlety: `x[0]` inside `x` itself is legal (the `t = 0` value is a
seed), but `x[5]` inside `x` is not, since at `t = 5` it is instantaneous. The rule is precise:
`At(x, k)` contributes a `lag = 0` edge *only for the period `t = k`*, so the engine checks
acyclicity of `G₀` with `At` edges included; if that fails, it reports the specific period and
suggests `init` or a lag.

**`init` edges.** `init` may reference stage-2 values (§8.2), which inverts the ordinary direction of
dependence. Those edges form their own graph `G_init`, and the rule is the same: `G_init` must be
acyclic (`E0202`, "cyclic dependency through `init`"). Chains are legal and are what the engine's
substage levels implement; a cycle is not.

**Error message shape** (Elm-grade is a requirement, not an aspiration):

```
error[E0201]: cyclic dependency in the same period

  reserve depends on bel, which depends on reserve — with no time lag between them,
  so neither can be computed first.

   ┌─ term_assurance.pir:41:12
41 │ expr = "bel * 1.05"
   │         ^^^ reserve reads bel at time t
   ┌─ term_assurance.pir:52:12
52 │ expr = "reserve + risk_adjustment"
   │         ^^^^^^^ bel reads reserve at time t

  Cycles across periods are fine. If `bel` should use last period's reserve, write:

52 │ expr = "reserve[t-1] + risk_adjustment"

  If this really is simultaneous, it cannot be expressed in a projection IR — solve it
  outside the loop and feed the result in as an assumption.
```

### 3.2 Evaluation order

Within `G₀`, evaluation order is the **deterministic topological order**: Kahn's algorithm with the
ready-set kept as a min-heap on `(module_path, declaration_index)`. Two structurally identical
models produce byte-identical evaluation orders regardless of hash-map iteration, thread count, or
platform. This is load-bearing for reproducibility and for diffing `explain()` traces.

Parallelism is over **modelpoints**, never over components within a modelpoint. Modelpoints are
independent by construction (there is no cross-modelpoint reference in the `Expr` grammar), so the
parallel and serial results are bit-identical.

## 4. Serialisation format

**Decision: the canonical on-disk form is `.pir`, a restricted TOML dialect, one file per module,
one `[[component]]` table per component, with formulas written in a small infix expression
language inside the `expr` string.**

Why this and not the alternatives:

- *Not JSON/protobuf ASTs.* A nested-array AST for `premium[t-1] * (1 + esc)` produces a 12-line diff
  when you change `1.05` to `1.04`. Diffability is the point of the whole exercise.
- *Not YAML.* Significant whitespace and the Norway problem; TOML's grammar has one reading.
- *Not raw Python.* The engine would need Python, WASM would be impossible, and the "no arbitrary
  code" rule would leak.
- *Infix formulas in strings* because that is what an actuary reads and what an LLM writes fluently.
  The expression grammar is small (§2.6), fully specified, and parsed by the same Rust parser in the
  engine, the CLI, and the browser.

A lossless JSON encoding (`pir.json`) exists for tooling that should not embed a parser. It is
*generated*, never authored, and is not committed by default.

### 4.1 Canonical form

`predictable fmt` is the arbiter; CI enforces it. Canonicalisation rules:

1. Key order within a `[[component]]` is fixed:
   `name, kind, dtype, shape, unit, timing, init, expr, doc, tags, output`.
2. Components appear in declaration order; `predictable fmt` never reorders them (declaration order
   is authorial intent and is the tiebreak in §3.2).
3. Expressions are normalised: single spaces around binary operators, no redundant parentheses
   *except* those that disambiguate mixed `*`/`+` precedence, which are preserved as written.
4. Floats round-trip via shortest-representation (Ryū); `1.05` never becomes `1.0500000000000001`.
5. UTF-8, LF, one trailing newline, no trailing whitespace.
6. Rule 3's normalisation is idempotent, so `fmt` is a fixed point after one pass.

### 4.2 Expression grammar

```
expr    := ternary
ternary := "if" expr "then" expr "else" expr | orexpr
orexpr  := andexpr ("or" andexpr)*
andexpr := cmp ("and" cmp)*
cmp     := sum (("==" | "!=" | "<" | "<=" | ">" | ">=") sum)?
sum     := product (("+" | "-") product)*
product := unary (("*" | "/") unary)*
unary   := ("-" | "not") unary | power
power   := atom ("^" unary)?
atom    := literal | call | lookup | ref | "(" expr ")"
ref     := IDENT index?
index   := "[" ("t" ("-" INT)? | INT) "]"
call    := IDENT "(" (expr ("," expr)*)? ")"
lookup  := IDENT "@" "(" expr ("," expr)* ")"      -- table lookup
```

`@` is the lookup sigil: `mortality_sa8990@(age, gender, smoker)` reads unambiguously and cannot be
confused with a function call, which matters because table names and builtin names live in different
namespaces.

## 5. Timeline

```toml
[timeline]
basis        = "monthly"        # monthly | annual | quarterly
periods      = 480              # T; the projection runs t = 0..=480
origin       = "policy"         # policy (t=0 at policy anniversary) | valuation (t=0 at val date)
valuation_date = 2026-06-30
year_convention = "act/365"
```

The timeline generates `Input.Timeline` components, always available, never redeclared:

`t`, `period_start_date`, `period_end_date`, `year_frac` (length of period `t` in years),
`month_of_year`, `policy_year` (1-based), `policy_month`, `is_anniversary`.

**Basis conversion is explicit.** A `rate(annual)` assumption used in a monthly model must pass
through `to_monthly()`, which is defined as `(1 + r)^(1/12) - 1` for `rate` units — compounding, not
division. `r / 12` on a `rate(annual)` is a definition-time error with the message naming both the
compounding conversion and the explicit `nominal_to_periodic(r, 12)` if simple division is genuinely
wanted. Prophet models are full of `/12`; the migration tool flags every one for the user to confirm.

Changing `basis` changes results and must therefore be a visible line in the diff, which it is.

## 7. Type checking

The checker runs in six passes, all before any modelpoint is read. Every diagnostic carries a code
(`E0xxx` error, `W0xxx` lint), a primary span, secondary spans, and at least one suggested edit.

1. **Parse** — grammar errors, with recovery so multiple errors surface per run.
2. **Resolve** — every `Ident` binds to a component, modelpoint field, assumption, table, or
   timeline input. Unresolved names get a Levenshtein suggestion restricted to the correct
   namespace. Shadowing across modules is an error, not a silent win.
3. **Cycles** — §3.1.
4. **Shapes** — broadcast lattice; narrowing without an aggregate is `E0301`.
5. **Types and units** — §2.4; `if` branch dtypes must unify; lookup key arity and dtypes must match
   the table declaration exactly.
6. **Lints** — unused components (`W0101`), `unit = "none"` on money-shaped arithmetic (`W0102`),
   timing mismatch in a sum (`W0103`), a `Series` with no dependence on any `PerMP` or lag
   (`W0104`: "this is constant across modelpoints and time; consider an assumption"), a timing
   operation applied to an untimed value (`W0105`, §2.5).

Passes 2–5 run over the product's module set (§8.4.1). A run file adds a seventh, run-scoped
validation — `emit_list` ids resolve, `[[aggregation]]` keys and measures have legal shapes,
`[[solve]]` targets and varied inputs resolve, no timeline field is overridden — which runs at
`predictable run` and at `predictable check <run>.pir`, and never at model-check time, so a model
stays checkable without a run.

Errors are emitted as human text on the terminal and as a machine-readable JSON array (`--json`)
whose entries are `{code, severity, message, spans, suggestions, doc_url}`. The JSON form is what an
LLM agent consumes in the migration loop; the suggestions are literal replacement edits with byte
ranges, so an agent can apply them mechanically and re-check.

## 8. Execution semantics

### 8.1 The projection loop

For each modelpoint, for `t = 0..=T`, evaluate stage-1 components in topological order. `Scalar`
and `PerMP` components are evaluated once, before the loop. Series values are retained for the whole
projection (memory is `n_series × (T+1) × 8` bytes per modelpoint — for 480 monthly periods and 200
series that is 768 KB, trivially fine).

### 8.2 Two-stage evaluation

`Agg` nodes reduce a completed `Series` to a `PerMP`. They therefore run in **stage 2**, after the
full `t` loop. A stage-2 component may be referenced by another stage-2 component (ordinary DAG),
and by a stage-1 component **only through `init`** — which is how `reserve` above seeds itself from
`bel`, a stage-2 npv. This is the single legal backward channel and it is checked: `init` may
reference stage-2 values; `expr` may not.

If a model needs genuine iteration to a fixed point (e.g. a solved-for premium), that is a *solver*
wrapped around the whole projection, declared in the run config, not a construct inside the IR. IR
1.0 supports `[[solve]]` blocks in the run file — `name`, `target`, `to`, `vary`, `scope`,
`tolerance`, `max_iter`, `method = "brent"`, `bracket` — with the schema and the manifest contract in
§8.4.4. The projection itself stays a pure function.

### 8.3 Portfolio aggregation

Aggregation across modelpoints happens strictly after all projections, in a declared
`[[aggregation]]` block. It cannot be expressed in an `Expr`, which is what guarantees modelpoint
independence and therefore embarrassing parallelism and bit-identical determinism.

**Schema** (Q4). `[[aggregation]]` blocks live in the run file (§8.4.2), not in a model module — they
are a property of what you are reporting, not of the model:

```toml
[[aggregation]]
name     = "bel_by_cohort"
group_by = ["product_code", "entry_year_band"]   # ordered; PerMP or Scalar components/fields
measure  = "bel"                                 # one component id
op       = "sum"                                 # sum | mean | min | max | count | weighted_mean
weight   = "num_pols_if"                         # required iff op = "weighted_mean"
filter   = "in_force_at_val"                     # optional; a bool PerMP component id
over_t   = "each"                                # each | total ; only for a Series measure
```

Rules, all checked before the run starts:

- **`group_by` keys are `PerMP` or `Scalar`**, of dtype `i64`, `bool`, `str`, `date` or `enum(...)`.
  A `Series` key is `E0402` — a group whose membership changes with `t` is not a group. `f64` keys are
  `E0403`; band it into an enum or an `i64` first.
- **Groupings do not nest.** `group_by` is one *ordered key tuple*, producing one flat row per
  distinct tuple. There is no parent/child aggregation and no subtotal row. A UI that wants a
  drill-down tree builds it by successive prefixes of the tuple, which is exactly why the list is
  ordered and why the order is preserved into `aggregates.parquet`'s `group_key`. Declaring both
  `["product"]` and `["product","cohort"]` as two blocks is legal and is how you ask for both levels.
- **`measure` is a single component id**, `PerMP` or `Series`. For a `Series` measure, `over_t`
  chooses between one row per `(group, t)` (`"each"`, the default) and one row per group summed over
  `t` (`"total"`). For a `PerMP` measure, `over_t` must be absent (`E0404`).
- **`op` is a monoid** (or a pair of monoids for `mean`/`weighted_mean`), which is what lets the
  runner fold chunks in any completion order and still get a bit-identical answer: partial results
  are combined in **chunk index order**, never in completion order, and `sum` accumulates
  sequentially in `mp_row` order within a chunk. `count` ignores `measure` but still requires it to
  resolve.
- **`filter`** names a `bool` `PerMP` component; excluded modelpoints contribute to no group. It is a
  component reference, not an expression, so that every predicate that affects a reported number is a
  named, diffable, explainable thing in the model.
- `name` is unique across the run file and is the `aggregation` id in the manifest and in
  `aggregates.parquet`.

`group_key` in the output is the group tuple rendered as `key1=value1|key2=value2` in `group_by`
order, with values in their canonical text form (§4.1). It is a join key; it is stable.

### 8.4 Products and run configuration

This section closes Q1, Q2, Q6, Q8 and Q15. Two new file kinds join the model module and the
assumption set, and both are `.pir` — the same restricted TOML, the same parser, the same digests.

#### 8.4.1 The `[product]` block

A **product** is a named entry point: the set of modules that constitute a model, and the manifest of
outputs it promises. Before this ruling it existed only as a Python call, which contradicted rule 2 —
deleting the DSL would have changed what a run *is*. It is now IR:

```toml
format = "pir/1"

[product]
name        = "TERM_UK"
modules     = ["term_assurance/schema", "term_assurance/model"]
outputs     = ["bel", "reserve", "net_cashflow", "pv_premiums", "pv_claims", "pv_expenses"]
key_field   = "policy_number"
assumptions = "assumptions/base"          # default set; a run may override
doc         = "UK level-term assurance, statutory valuation basis."
```

- `modules` is the closed module set: exactly the modules loaded, in the order given, and that order
  is the `module_path` order used by §3.2's tiebreak and by `model_digest` (§9.6). A module reached
  by `imports` but absent from `modules` is `E0105`.
- `outputs` is the **validated manifest** described in §2.2, not a selector. It must equal the set of
  `kind = "Output"` components across `modules`, or `E0107`. Its purpose is that a reviewer of the
  product file sees the promised result set without reading every module, and that adding an
  `Output` shows up as a diff in *two* places.
- `key_field` names the `modelpoint_field` with `key = true`; it is restated here because the results
  join key must be knowable from the product alone.
- A product file declares no components and no timeline. `model_digest` covers the product file
  along with its modules.

#### 8.4.2 The `[run]` block — canonical `RunConfig`

**`[timeline].periods` is the only normative source of `T`.** A run config that tries to set
`periods`, `basis`, `origin`, `valuation_date` or `year_convention` is `E0101` ("the timeline is a
property of the model, not of the run"); changing the projection length is a model change and must
appear in `model_digest`. This resolves the two-homes problem in Q1 in favour of the model.

```toml
format = "pir/1"

[run]
product      = "products/term_uk"          # path to the product file
assumptions  = "assumptions/base"          # overrides product.assumptions
modelpoints  = "data/term.mpf.parquet"
out          = "runs/2026-06-30-base"

emit         = "outputs"                   # outputs | all | list
emit_list    = []                          # required iff emit = "list"
retain       = "ring"                      # ring | full
storage_precision = "f64"                  # reserved; "f32" is E0108 in IR 1.0

on_trap      = "abort"                     # abort | continue
max_errors   = 100
allow_table_drift = false
sum_kahan    = false

[run.tables]                               # per-table source override; digest may not be overridden
sa8990 = "resource:sa8990_2026"

[run.exec]                                 # non-semantic; excluded from run_digest
threads    = 8
chunk_size = 1024
progress   = true

[[solve]]
name      = "premium_solve"
target    = "bel"
to        = 0.0
vary      = "annual_premium"
scope     = "per_mp"                       # per_mp | portfolio
tolerance = 1e-8
max_iter  = 50
method    = "brent"
bracket   = [0.0, 1.0e6]

[[aggregation]]
name     = "bel_by_cohort"
group_by = ["product_code"]
measure  = "bel"
op       = "sum"
```

**`run_digest`** is SHA-256 over the canonical text of the `[run]` file with `[run.exec]`, `out`, and
`run.progress` removed. The partition is a rule, not a list to be maintained by hand:

> A field participates in `run_digest` **iff changing it can change a number in `results.parquet`**.

So `threads`, `chunk_size` and `progress` are excluded (`run(threads=1) ≡ run(threads=64)` bit for
bit — §9.1 — and if that ever stops being true it is a P0 bug, not a digest question), `out` is
excluded (where results are written is not what they are), and everything else is included:
`product`, `assumptions`, `modelpoints`, `emit`, `emit_list`, `retain`, `storage_precision`,
`on_trap`, `max_errors`, `allow_table_drift`, `sum_kahan`, `[run.tables]`, every `[[solve]]` and every
`[[aggregation]]`. `max_errors` and `on_trap` are in because they can truncate a result set;
`retain` is in because `retain = "ring"` makes non-emitted series unavailable to `explain()` replay
and so changes what the run set *contains*.

Reproducibility is therefore `(model_digest, assumption_digest, modelpoint_digest, table_digests,
run_digest, engine_version)` — §9.4's manifest carries all six.

#### 8.4.3 `emit` is structural, and the diff knows it (Q6)

`emit` changes which components appear in a result set without changing `model_digest`, which would
make two runs of one model look structurally incomparable for a reason buried in the run config. The
ruling has three parts:

1. `emit` is a `run_digest` field (above), so the difference is never invisible.
2. Every result set carries `results.component_set_digest`: SHA-256 over the sorted list of emitted
   qualified component ids. Two result sets with equal `component_set_digest` are directly
   comparable; unequal ones are not, and the digest says so in one comparison rather than a set diff.
3. An `emit` mismatch is a **named, first-class condition**, not a structural error. `predictable
   diff` reports `emit_mismatch` in `diff.json`, compares the intersection, lists the components
   present on only one side, and exits `0`/`1` on the intersection's tolerance outcome — never `2`.
   `--require-same-emit` restores the strict behaviour. `04-verify.md` §5 owns the rendering.

`emit = "outputs"` (default) emits `kind = "Output"` components. `emit = "all"` emits every `Derived`
and `Output` component — the migration mode. `emit = "list"` emits `emit_list` ∪ outputs; each id must
resolve, or `E0106`. `emit` never *removes* an `Output` from the result set; there is no way to
produce a result set that does not honour the product's promised manifest.

#### 8.4.4 `[[solve]]` and its manifest contract (Q8)

A solve is a root-find wrapped around the projection: for each modelpoint (`scope = "per_mp"`) or for
the portfolio once (`scope = "portfolio"`), vary `vary` until `target` equals `to` within `tolerance`.
`vary` must name a `Input.Modelpoint` field or a `Scalar` `Input.Assumption`; `target` must name a
`PerMP` (per-mp scope) or an `[[aggregation]]` name (portfolio scope). The projection stays a pure
function of its inputs; the solver is strictly outside it.

A solved run is only reproducible if the solve's own outcome is recorded, so the following is
normative and `04-verify.md` §6.2's `run_config.solves` is typed by it:

```jsonc
"solves": [
  {
    "name": "premium_solve",
    "target": "term_assurance.bel", "to": 0.0,
    "vary": "annual_premium", "scope": "per_mp",
    "method": "brent", "tolerance": 1e-8, "max_iter": 50, "bracket": [0.0, 1000000.0],
    "converged": 9998,                 // modelpoints that met tolerance
    "not_converged": 2,                // modelpoints that hit max_iter
    "iterations": {"min": 4, "max": 50, "mean": 7.2, "total": 72431},
    "residual": {"max_abs": 4.1e-9, "argmax_mp": "POL03917"},
    "per_mp": {"path": "solves/premium_solve.parquet", "digest": "sha256:1d7c…"},
    "on_not_converged": "warn"         // warn | error
  }
]
```

`solves/<name>.parquet` has columns `mp_key, mp_row, solved_value, residual, iterations, converged`
and is written whenever `scope = "per_mp"`. For `scope = "portfolio"`, `iterations`, `residual` and
`solved_value` are scalars and no side file is written. The solved value is *also* materialised as an
ordinary `PerMP` component named `<solve.name>` in `results.parquet`, so downstream joins do not have
to special-case solves. `on_not_converged = "error"` (the default for `scope = "portfolio"`) fails
the run with `E0903`.

#### 8.4.5 Storage precision (Q15)

`run.storage_precision` is **reserved in IR 1.0 and accepts only `"f64"`**; `"f32"` is `E0108`
("output-only f32 storage arrives in IR 1.1"). It is specified now, and rejected now, purely so that
the key exists in the grammar and 1.1 can enable it as a minor bump rather than a format change.
When enabled, it will affect the *written* `value` column only — all arithmetic stays `f64` per §2.4
— and it will remain a `run_digest` field, because it changes the bytes a consumer reads. `T14`
writes `double` unconditionally in 1.0 and must not pre-emptively add an `f32` path.

## 9. Determinism

Reproducibility is a testable property, and the IR is designed so that it holds by construction.

1. **Order.** Deterministic topological order (§3.2). Modelpoint results are written in modelpoint
   file order regardless of completion order.
2. **Floating point.** All arithmetic is IEEE-754 `f64`, round-to-nearest-even. No FMA contraction
   (the engine builds with contraction off), no `-ffast-math`, no reassociation. Reductions (`sum`,
   `npv`) are **sequentially left-to-right in `t` order** — no pairwise or SIMD reordering — because
   an actuary reconciling to Prophet to the penny must get the same answer on every machine, and a
   0.5 ULP difference from a reordered sum is a support ticket. Where higher accuracy matters,
   `sum_kahan` is an explicit, separately-named builtin.
3. **Traps.** Division by zero, `ln` of non-positive, `pow` producing NaN, and lookup misses under
   `on_missing = "error"` all raise a runtime error naming the component, the modelpoint key, and
   `t`. NaN and ±Inf never silently enter results. (v0 propagated NaN through pandas joins; that is
   precisely the bug class being designed out.) The reporting envelope is §9.3.1.
4. **Run provenance.** Every result set carries a manifest:
   `{ir_version, engine_version, model_digest, assumption_digest, modelpoint_digest, table_digests,
   run_digest, timeline, run_config, lineage, started_at, outcome}`. `started_at` is the only
   non-deterministic field and is excluded from result comparison. Re-running the same manifest on
   the same engine version yields byte-identical output; on a *different* engine version, the diff
   tool says so first. The full schema is normative in `04-verify.md` §6.2; §9.4 below fixes the
   three fields the IR requires it to carry.
5. **No hidden state.** No global mutable settings. v0's `precision.get_precision()` global is
   removed: rounding is an explicit `round(x, dp)` in the expression, visible in the diff.
6. **Digests.** `model_digest` = SHA-256 over the *canonical* text of all modules in path order.
   Formatting-only changes therefore do not change the digest — `fmt` is applied before hashing.
   The product file (§8.4.1) is included; the run file is not — it has its own `run_digest` (§8.4.2).
7. **Determinism targets.** `x86_64-unknown-linux-gnu`, `aarch64-apple-darwin` and **`wasm32-wasip1`
   under wasmtime** are all supported determinism targets, and the golden corpus runs byte-equality
   assertions on all three in CI. `wasm32` is named explicitly because the governance-pack and static
   export story (`05-viz.md` §1.5) depends on the browser reproducing the server's numbers.

### 9.3.1 Trap reporting and policy (Q7)

A trap is a *modelpoint-level* failure with a *run-level* default policy. Both halves matter: the
unit of invalidity is the modelpoint, because nothing crosses modelpoints (§3.2); but the default
must be loud, because a silently short result set is the hazard.

```jsonc
{
  "code": "E0902",
  "severity": "error",
  "kind": "trap",
  "trap": "div_by_zero",        // div_by_zero | log_non_positive | pow_nan | lookup_miss
                                // | index_out_of_range | overflow_to_inf | not_finite
  "component": "term_assurance.qx",
  "expr_path": "expr.lhs",       // §3.0.1
  "span": {"file": "model.pir", "line": 41, "col_start": 8, "col_end": 34},
  "mp_key": "POL00042",
  "mp_row": 41,
  "t": 17,
  "message": "division by zero evaluating `num_pols_if / exposure` at t = 17",
  "operands": {"lhs": 0.994, "rhs": 0.0},
  "doc_url": "https://predictable.dev/diagnostics/E0902"
}
```

`run.on_trap` (§8.4.2) selects the policy:

- **`abort` (default).** The trap is reported, the run stops, exit code `2`, and **no
  `results.parquet` is written** — a partial result file is never produced under `abort`. A
  `manifest.json` *is* written, with `"outcome": "aborted"` and the trap in `execution.traps`, so the
  failure is as documented as a success.
- **`continue`** (`--continue-on-trap`). The trapping modelpoint is abandoned at the trap: it
  contributes **no rows at all** to `results.parquet`, no null rows (there are no nulls — §2.11), it
  is excluded from every `[[aggregation]]`, and it is recorded in `execution.traps[]`. The run
  finishes with `"outcome": "completed_with_traps"` and exit code `1`. `manifest.results.rows` and
  `execution.modelpoints_projected` count only the surviving modelpoints, and
  `execution.modelpoints_trapped` counts the rest.

`--max-errors N` caps the number of distinct trap reports retained (default 100); the *counts* stay
exact. Because traps are detected per lane via `TrapFlags` and then replayed scalar-wise for the
diagnostic (`03-engine.md` §5.5), the message above is reproducible and its operand values are the
real ones, not a re-derivation.

`manifest.outcome` is one of `"completed"`, `"completed_with_traps"`, `"aborted"`, `"cancelled"`. A
cancelled run (the runner's cancel flag, `03-engine.md` §10) writes the manifest with
`"outcome": "cancelled"` and `execution.modelpoints_projected` short of the file's row count: a
truncated result set that looks complete is a real hazard and this is the fix.

### 9.4.1 Manifest fields the IR requires

`04-verify.md` §6.2 owns the manifest schema. Three of its fields are fixed here because they are IR
concepts rather than reporting concepts.

**`run_digest`** (§8.4.2) sits alongside `model_digest` in `inputs`, and `manifest_digest` covers it.

**`lineage`** (Q12). A sensitivity fan is N runs that share a parent, and inferring that from
filenames is not acceptable for something a regulator reads. Every manifest carries:

```jsonc
"lineage": {
  "parent_run": "2026-08-17T09:14:22Z-3f0a",          // null for a base run
  "parent_manifest_digest": "sha256:3f0a…",           // null for a base run
  "group_id": "sens-2026-06-30-mort",                 // null when not part of a set
  "label": "mortality +10%",
  "varied": [
    {"path": "assumptions.mortality_loading", "from": 1.0, "to": 1.1}
  ]
}
```

`varied` entries use dotted paths into the run's inputs (`assumptions.<name>`,
`run.tables.<name>`, `run.<field>`, `modelpoints`), with `from` and `to` in canonical text form.
`predictable run --sensitivity` populates all of it; a hand-run child sets `parent_run` and the tool
computes `varied` by diffing the two manifests, so `varied` is always *derivable* and never the only
record. Consumers group a fan by `group_id`, order it by `varied`, and never parse a filename.

**Table content travels with the result set** (Q13). Every table actually read during a run is copied
into `run/tables/<name>.parquet`, and `manifest.inputs.tables[]` gains `{"copy": "tables/sa8990.parquet",
"copy_digest": "sha256:…"}`. This is not optional bookkeeping: `explain()` shows the resolved row of a
lookup (§11.2), and a static export or an archived run with no access to the original CSV cannot show
that row otherwise — the trace would degrade to "some row, value 0.00214", which is precisely the
silent-wrongness surface tables are dangerous for. `--no-table-copy` suppresses it for large tables
and stamps `"copy": null`, and any consumer that finds `copy: null` must say "table content
unavailable in this run" rather than rendering a partial row. Copies are written through the same
`TableResolver` bytes that were hashed (§2.9.1), so the copy is provably what was used, not a re-read.

## 10. Versioning

Every file begins `format = "pir/N"`. The IR follows semver on `IR_VERSION = MAJOR.MINOR`:

- **Minor bump** (`1.0` → `1.1`): new builtins, new optional component fields, new unit tags, new
  table policies. Old files load unchanged. A new engine reads all older minors of its major.
- **Major bump** (`1.x` → `2.0`): grammar changes, semantic changes, removals. The engine reads the
  previous major and refuses anything older, pointing at `predictable migrate`.
- **`predictable migrate --to 2.0`** performs mechanical upgrades and writes the new `format` line.
  Migrations are pure text-to-text and are themselves tested by round-tripping the example corpus.
- **Semantic changes never happen silently under a fixed version.** If period-0 handling of `npv`
  changes, that is a major bump, full stop. Actuaries' regression packs depend on it.
- The engine's own version is separate and recorded in the run manifest; two engine patch versions
  must produce identical results for the same IR version, and the golden-model corpus enforces it in
  CI.

## 11. Metadata for `explain()` and diffing

**Ownership of downstream artefacts.** This section defines what the IR must *carry*; the on-disk
schemas of the artefacts built from it are normative elsewhere and are not restated here:

| Artefact | Normative in |
|---|---|
| Results schema (`results.parquet`, `results.schema.json`) | `04-verify.md` §2 |
| `explain()` trace JSON, closed node-variant list, `N0xxx` notes | `04-verify.md` §3.2 |
| Run diff JSON (`RunDiffDoc`), hypotheses, tolerance profiles | `04-verify.md` §5 |
| Run manifest JSON | `04-verify.md` §6 |
| `GraphDoc` (`predictable graph --json`) | `05-viz.md` §2.1 |

Each of those is a pure function of the IR plus a run; none may introduce a concept the IR lacks.

### 11.1 Spans and provenance

Every `Expr` node carries a `Span { file, byte_start, byte_end, line, col }`, assigned at parse
time and preserved through checking. Every component carries:

```toml
[component.meta]
id      = "01J8Q2K7..."                   # optional stable identity, survives renames
doc     = "Best estimate liability."
tags    = ["ifrs17", "bel"]
authored_by = "dsl"                       # dsl | hand | migration
source  = { system = "prophet", library = "TERM_UK", variable = "BEL_TOT", file = "TERM.VAR:118" }
origin_span = { file = "reserves.py", line = 34, col_start = 12, col_end = 44 }
overrides   = { library = "acme", version = "3.2.0", component = "qx_loading" }
generated_from = { file = "expenses.py", line = 61, iteration = "band_A" }
display = { dp = 2, scale = 1.0 }         # rendering only; never affects computation
```

All of these are optional and none participate in evaluation. Three earn specific rules:

- **`origin_span`** is the authoring-language span (Python, or a Prophet source line). Every
  diagnostic the checker raises against a component or an `Expr` node **must** be renderable against
  `origin_span` when present, and against the `.pir` span otherwise. Per-`Expr`-node origin spans are
  carried in a side table (`ExprId → origin_span`) emitted alongside the module. Without this the DSL
  cannot show an `E0201` cycle error against the two Python bodies that caused it, which is the whole
  point of the layer — so it is a requirement, not a convenience.
- **`id`** is an optional opaque stable identity written by the DSL and preserved across renames. It
  is excluded from `model_digest`. When present it is the join key for graph-layout caches and
  cross-run comparison; when absent, consumers fall back to the qualified name plus §11.3's rename
  heuristic.
- **`display`** is explicitly non-semantic. It changes rendering in the UI and in diff reports only,
  and is excluded from `model_digest`.

`source` is written by the Prophet migration tool and is the backbone of the migration demo: every
component states which Prophet variable it came from, so a reviewer can go line by line, and a
coverage report can list Prophet variables with no corresponding component.

### 11.2 `explain()` traces

`explain(component, modelpoint, t)` returns a tree, not a string:

```json
{
  "component": "reserve", "t": 3, "modelpoint": "POL00042",
  "value": 1284.55, "unit": "money", "timing": "point",
  "expr": "(reserve[t-1] + premium_income[t-1] - death_claims[t-1] - renewal_expenses[t-1]) * (1 + valuation_rate)",
  "span": {"file": "model.pir", "line": 148},
  "children": [
    {"node": "Lag", "ref": "reserve", "lag": 1, "t": 2, "value": 1180.11},
    {"node": "Lag", "ref": "premium_income", "lag": 1, "t": 2, "value": 312.40,
     "children": [
       {"node": "Ref", "ref": "premium_rate", "t": 2, "value": 330.75},
       {"node": "Ref", "ref": "num_pols_if", "t": 2, "value": 0.9447}
     ]},
    {"node": "Ref", "ref": "valuation_rate", "kind": "Assumption", "value": 0.035,
     "assumption_set": "base"},
    {"node": "Lookup", "table": "sa8990", "keys": {"age": 47, "gender": "M", "smoker": false},
     "row": 312, "value": 0.00214, "policy_applied": "exact"}
  ]
}
```

Traces are produced by a **replay** of the single modelpoint with recording enabled, not by taping
every value of every run — so tracing costs nothing in the hot path, and the replay is guaranteed to
reproduce the traced value because the projection is deterministic (§9).

Recorded per node: value, unit, timing, span, `expr_path` (§3.0.1), and for lookups the resolved row
and the key policy that fired (clamped/stepped lookups are where silent wrongness lives).

**`Agg` nodes must retain per-`t` contributions** (Q11). This is a requirement on the recording
evaluator, not an option, because it is what makes a discounting bug findable: a `bel` that is 3%
wrong tells you nothing, whereas a `terms` array whose discount exponent is `v^t` where it should be
`v^(t+1)` tells you everything in one glance.

```jsonc
{"node": "Agg", "op": "npv", "ref": "premium_income", "timing_used": "start",
 "value": 4182.77, "term_count": 40,
 "terms": [
   {"t": 0, "value": 500.00, "disc": 1.0,     "contribution": 500.00},
   {"t": 1, "value": 486.21, "disc": 0.96618, "contribution": 469.77}
 ]}
```

Normative details:

- `terms` is present for every `Agg` node in a trace, in ascending `t`, with no gaps, and its
  `contribution` values sum left-to-right to `value` **exactly** — the recorder replays the same
  sequential reduction as the kernel (§9.2), it does not re-add the terms in a different order.
- `disc` is present for `npv` only, and is the discount factor *after* the timing exponent of §2.5
  has been applied, with `timing_used` naming the timing that chose it. The exponent is the bug; it
  must be visible as data.
- For predicated aggregates (`sum(x, cond)`, `count_while`) each term carries
  `"included": true|false`, and `count_while` marks the first excluded term `"stopped_here": true`.
- `--trace-max-terms N` (default `4096`) truncates long series, setting `"terms_truncated": true` and
  keeping the first and last `N/2` terms. Truncation is never silent.
- This costs nothing in the hot path: `terms` exists only under replay recording, which runs for one
  modelpoint on demand. The kernel's own reduction is unchanged and must not be made to carry it.

### 11.3 Model diffing

`predictable diff modelA modelB` operates on the IR, not the text, so it reports *semantic* change:

- Components added / removed / renamed (rename detected by identical normalised `expr` and `unit`).
- For changed components: the expression diff at AST level, classified as
  `formula`, `timing`, `unit`, `dtype`, `shape`, `init`, `doc-only`.
- Table digest changes, with a row-level diff of the CSV.
- Assumption value changes.
- **Impact set**: the transitive downstream closure of every change, so the output is "these 3
  changes affect 14 components and 4 outputs, of which `bel` and `reserve` are Outputs."

`predictable diff runA runB` (the Prophet `.rpt` run-diff) joins on modelpoint key and component
name, reports absolute and relative differences with configurable tolerance, ranks by contribution
to the total movement, and — the part that matters — cross-references the model diff to attribute
each movement to a specific changed component where the impact set makes that unambiguous. Prophet
`.rpt` files are read into the same result schema, so `predictable diff prophet.rpt run/` is the
migration verification loop.

## 12. Non-goals for IR 1.0

Stated so they are not accidentally designed in:

- Stochastic scenario dimension. A scenario axis is a 1.1 addition (`Shape::Series` gains an
  optional scenario rank); the expression grammar is already scenario-agnostic.
- Cross-modelpoint references (group policies, reinsurance treaties spanning policies). Handled by
  the aggregation stage, or by a second model pass, not inside a projection.
- User-defined functions. Deliberate: inlining is the DSL's job, and a flat graph is what makes
  `explain()` and diff comprehensible.
- Nested/ragged data on a modelpoint (funds, riders as sub-records). Planned for 1.2 via a declared
  sub-modelpoint axis with explicit fold operations.
- Runtime nulls and three-valued logic (§2.11). Missingness is a boundary concern, permanently.
- Output-only `f32` storage (§8.4.5). Reserved in the grammar, rejected by the checker, enabled in 1.1.

# Demo 1 — a Prophet migration, executed

This directory contains a **real, executed** migration of an FIS Prophet library into
predictable, driven by [`skills/predictable-migration`](../../skills/predictable-migration/SKILL.md),
and reconciled to the penny against the Prophet run it came from.

It is not a description of a migration. Every command below is in
[`run_demo.sh`](run_demo.sh); the script replays the whole thing from the raw Prophet files
and **fails if the final diff is not clean**. That script is the screencast source.

```console
$ ./demos/migration/run_demo.sh
...
MIGRATION DEMO: OK
```

---

## What is being migrated

`TERM_UK` — level term assurance, annual, 40 periods, 16 model points — as five files:

| file | what it is |
|---|---|
| `prophet/TERM_UK.MOD` | the library source: 20 variable definitions, the authority for every *formula* |
| `prophet/TERM_UK.mpf` | the model point file: 16 policies, 9 fields |
| `prophet/SA8990.fac` | mortality, 3 dimensions (age 18-100 x sex x smoker), 332 cells |
| `prophet/LAPSE_TERM.fac` | lapse rates by policy year |
| `prophet/EXP_BAND.fac` | servicing expense scaling by band |
| `prophet/TERM_BASE_2026Q2.rpt` | **the run to reconcile to** — the authority for every *number* |

Those files are synthetic, and it matters exactly how. They are generated by
[`tools/make_prophet_run.py`](tools/make_prophet_run.py), whose `project()` function is a
plain-Python transcription of `TERM_UK.MOD` written against the `.MOD` text and nothing
else — no predictable import, no shared code, no copied constants beyond the ones the `.MOD`
file itself declares. When the two agree to the penny at the end of this page, it is
because two independent implementations of the same specification agree, which is the only
version of that claim worth making.

The `.rpt` is written the way Prophet writes one: periods numbered from **1**, money to
**two decimals**, rates to ten, and one working variable (`RESERVE_INT`) that exists because
the run settings say so and is consumed by nothing.

---

## Step 0-1. Inventory before writing anything

The skill's first rule is that you do not open an editor on a `.pir` file until you can name
every Prophet variable you are expected to reproduce, and every one you are deliberately
not. That inventory is [`migration/coverage.json`](migration/coverage.json):

```console
$ python tools/import_prophet_inputs.py
model points :    16  -> data/modelpoints.csv
SA8990       :   332  -> tables/mortality.csv
LAPSE_TERM   :    40  -> tables/lapses.csv
EXP_BAND     :     3  -> tables/expenses.csv

$ cat migration/coverage.json | jq -r '.variables | to_entries[] | "\(.key)=\(.value|length)"'
mapped=10 derived=9 out_of_scope=1
```

20 variables in, 20 accounted for. `out_of_scope=1` is `RESERVE_INT`, and it is declared
`unmapped` in `migration/mapping.toml` **with a reason**, so the differ later reports it as a
known absence rather than as a gap.

Three translations are made here, and each is a decision written down rather than inferred:

* `SEX` is a Prophet integer code (1 / 2). predictable carries the rating factor itself, so
  it becomes `M` / `F` — the mortality table is keyed on the same values, so the code never
  has to be decoded twice.
* `SMOKER` is `Y`/`N` in the MPF and a genuine `bool` in the schema.
* `SA8990` holds the **unloaded** table rate. `MORT_LOAD = 1.05` stays in `base.pir` as an
  assumption, because it is a valuation basis item and a sensitivity has to be able to move
  it. (This is also, as it turns out, exactly where iteration 1 goes wrong.)

## Step 2-4. Schema first, then formulas, leaves upward

`model.py` is written schema-first: the timeline, the model point class, the assumptions and
the three tables, checked before a single formula, so that a misnamed field produces one
resolution error rather than one per formula that reads it.

Then the formulas, working up the dependency order — decrements, survivorship, cashflows,
discounting, reserves — with each component's docstring quoting the `TERM_UK.MOD` line it
came from. Two translations in that pass deserve calling out, because they are the ones
where Prophet and predictable genuinely differ rather than merely spell things differently:

**Timing is a decision, not a default.** Prophet has no timing tags: `PREM_INC` and
`DTH_CLAIM` are just numbers in a column, and whether a claim falls at the start or the end
of the policy year lives in the modeller's head and in `PV_CLM`'s discounting. predictable
requires `timing=` on every series, so the decision is made once, visibly:
`premium_income` is `START`, `death_claims` is `END`. That single fact then propagates —
`npv` discounts an `END` flow one period further than a `START` flow automatically, which is
why `PV_CLM` in the `.MOD` file reads `SUMALL(DTH_CLAIM * DISC(t+1))` and `PV_PREM` does
not. In Prophet that `(t+1)` is a convention you have to remember; in predictable it is a
consequence of a tag you already had to write.

**`LAPSE_TERM(t + 1)` becomes `lapses(policy_year)`.** Prophet indexes the lapse table with
an arithmetic expression on `t`. predictable has `policy_year` as a timeline builtin, and
using it is what stops the key silently drifting if this model is ever re-based to monthly.

## Step 5. Run, and diff — iteration 1

```console
$ python -m predictable build steps/iteration1/model.py --out build_iter1
built 4 file(s) into build_iter1: model.pir, product.pir, schema.pir, spans.json

$ predictable check build_iter1
3 file(s) checked, no diagnostics

$ predictable run run_iter1.pir --retain-all
run_id        2026-08-17T10:40:11Z-c9ca8e97
out           runs/iter1
outcome       Completed
modelpoints   16 projected, 0 trapped, of 16
results       9280 row(s), 20 component(s)
```

Note `emit = "all"` in `run_iter1.pir` and `--retain-all` on the command line. "Which
component is the root" is partly a fact about what the run was asked to write down: with
`emit = "outputs"` the differ cannot localise to `qx`, because `qx` was never written, and it
will name the nearest output downstream of it instead. That costs a step of localisation
every iteration.

The model checks clean. It also happens to be wrong in two places.

```console
$ predictable diff run prophet/TERM_BASE_2026Q2.rpt runs/iter1 \
      --mapping migration/mapping.toml --tolerance-profile reconcile
```

Read `F003` closely, because it is the whole thesis of the tool in one finding.

* `qx` diverges at **t = 0** and never stops — 656 cells, every model point, every period.
* The ratio `b/a` is **constant at 0.952380952 on all 41 periods, on 15 of 15 sampled model
  points**. A constant ratio is not "the numbers are a bit off"; it is a *scale* difference,
  which is a much narrower class of bug than a behavioural one.
* `0.952380952 = 1 / 1.05`. The differ does not know that `MORT_LOAD` is 1.05 — it never
  read the Prophet run settings. It inferred the factor from the numbers and proposed the
  reciprocal as an edit, anchored at a byte range in the generated `.pir`.
* Six of the nine findings are classified `inherited` — the same error seen further
  downstream, which will disappear when its root is fixed. Fixing them individually is how a
  migration takes three weeks.

`F002` is the second real error: renewal expenses are 2.7% high at `t = 0` and stay 2.7%
high. `EXP_PP` is quoted *at the valuation date*, so the first projection year is not
inflated; iteration 1 wrote `compound(expense_inflation, t + 1)` instead of `t`. The differ
does not diagnose that one to a character, but it tells you the component, the exact
timestep it starts at, that it is a constant proportion, and that nothing upstream of it
moved — which is enough.

`F001` (`reserve`) is worth a note about honesty. It is classified `root` with
`class_basis = "partial_graph"`: `reserve`'s value at `t = 0` is its `init`, which is `bel`,
which is a component the Prophet report does not contain. The differ says so — it does not
claim `ir_graph` certainty it does not have — and once the two genuine roots are fixed
`reserve` reconciles with them.

**No tolerance was touched.** `reconcile` is `abs 0.005` — half a penny — and the ground
rule of the skill is that widening it to clear a finding converts an unexplained difference
into an invisible one.

## Step 6. Fix the roots, re-run — iteration 2

Two edits, both in the components the differ named:

```diff
-    return mortality(age, sex, smoker)
+    return mortality(age, sex, smoker) * mortality_loading
```

```diff
-        * compound(expense_inflation, t + 1)
+        * compound(expense_inflation, t)
```

`steps/iteration1/model.py` is kept in the repository, unedited, so the two versions can be
diffed structurally as well as numerically:

```console
$ predictable diff model build_iter1 build
```

Then rebuild, re-run, re-diff:

```console
$ python -m predictable build model.py --out build
$ predictable run run.pir --retain-all
$ predictable diff run prophet/TERM_BASE_2026Q2.rpt runs/base \
      --mapping migration/mapping.toml --tolerance-profile reconcile

  a  prophet      TERM_BASE_2026Q2       /tmp/predictable-rpt-a-63729c2b
  b  predictable  2026-08-17T10:40:11Z-c8988a21 runs/base
  tolerance  reconcile   abs 0.005  rel 0.000001   mapping migration/mapping.toml
  component sets         a `outputs` vs b `all` — diffing the 10 in common

  MATCHED   0 of 6,560 cells   0 root divergences

  only in a   prophet.reserve_int  (declared unmapped)
  only in b   model.age  (unmapped)
  only in b   model.bel  (unmapped)
  ...
```

**0 of 6,560 cells.** `max |a − b| = 0.0` — every mapped number, on every one of the 16
model points, on every one of the 41 periods, is identical to what the `.rpt` recorded, at
the precision the `.rpt` recorded it.

The `only in b` list is not noise: those are the components predictable computes that Prophet
never reported. They are visible, named, and unmapped-by-omission rather than unmapped-by-
declaration — the differ distinguishes the two, and `RESERVE_INT` is the only entry on either
side carrying a written reason.

## Step 7. The stop condition

The skill's step 7 is four booleans, and they all hold:

| condition | result |
|---|---|
| `verdict = "matched"` at the `reconcile` profile | yes — `migration/diff_final.json` |
| every Prophet output variable mapped, derived or declared out of scope | yes — `migration/coverage.json`, 10 / 9 / 1 |
| `predictable check` clean of errors and of `W0102` unit lints | yes — `3 file(s) checked, no diagnostics` |
| no tolerance widened | yes — `tolerance.loosened = 0`, `mapping.adjusted = []` |

`run_demo.sh` asserts all of these plus twelve more, and exits non-zero if any fails.

### One caveat, stated rather than hidden

`summary.outputs[]` in `diff_final.json` reports portfolio *totals* that differ by up to
**6.3 pence** across the whole book — for example `renewal_expenses` totals 9,872.52 on the
Prophet side and 9,872.5716 on ours. That is not a modelling difference: it is 656 values
each rounded to two decimals in the `.rpt`, summed. No individual cell diverges, which is
why the verdict is `matched`, and the aggregate row is left in the report rather than
suppressed, because "the cells agree and the totals do not, by this much, for this reason"
is a thing a reviewer should be told.

### What is *not* claimed

`TERM_UK` is 20 variables. The skill's success metric is a ~50-variable library in under an
hour, and this demo is deliberately smaller than that: it is sized to be *auditable in one
sitting* — a reader can check the `.MOD` file against `model.py` line by line — rather than
sized to be impressive. Nothing here exercises Prophet constructs the readers refuse to
guess at (ambiguous dates, `P0109`; table orientation, `P0202`), and a real library will hit
them; that is what `references/prophet-idioms.md` is for.
